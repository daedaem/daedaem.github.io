> 코드와 테이블명은 문제의 구조를 보여주기 위해 일반적인 형태로 옮긴 것이다. 실제 시스템의 코드가 아니다.

Flash 기반 모듈이 하나 남아 있었다. Flash는 지원이 끝났고 브라우저에서 실행되지 않으니 손을 대야 했다.

선택지는 두 가지였다. 같은 기능을 다시 만들거나, 이미 같은 데이터를 다루고 있는 다른 시스템과 연동해 대체하거나. 후자를 골랐다. 이 판단 자체도 쓸 얘기가 있지만, 이 글의 본론은 그 다음이다.

전환한 결과를 기존 화면과 대조하는 검증 단계에서, **일부 건의 금액이 음수로 표기됐다.** 실제로는 큰 양수여야 할 값이었다.

## 음수는 어디서 오는가

금액 계산에 뺄셈이 없었다. 합계를 구하는 로직인데 결과가 음수로 나온다면, 뺄셈의 결과가 아니라 **값이 표현 범위를 넘어간 것**을 의심해야 한다.

Java의 `int`는 32비트 부호 있는 정수다. 표현 범위는 다음과 같다.

```
Integer.MIN_VALUE = -2,147,483,648
Integer.MAX_VALUE =  2,147,483,647
```

약 21억이다. 원 단위 금액에서 21억은 큰 수가 아니다. 계약 금액이나 누적 합계라면 어렵지 않게 넘는다.

그리고 Java는 정수 연산이 범위를 넘어갈 때 **예외를 던지지 않는다.** 조용히 한 바퀴 돌아 음수가 된다.

```java
int max = Integer.MAX_VALUE;   //  2147483647
System.out.println(max + 1);   // -2147483648
```

이게 오버플로다. 최상위 비트가 부호 비트인 2의 보수 표현에서, 최댓값에 1을 더하면 부호 비트가 켜지면서 최솟값으로 넘어간다. 자릿수가 넘쳐 사라지는 게 아니라 **부호가 뒤집힌다.** 그래서 큰 양수를 기대한 자리에 음수가 찍힌다.

예외가 없다는 점이 이 버그의 성격을 결정한다. 터지지 않으니 로그에도 안 남고, 값이 조용히 틀린 채로 흘러간다. 금액이 음수라서 눈에 띈 것이지, 오버플로가 두 번 일어나 다시 양수가 됐다면 검증에서 걸리지 않았을 수도 있다.

## DTO의 타입

문제의 DTO는 이런 모양이었다.

```java
public class ContractDto {
    private String contractNo;
    private int amount;        // 여기
    // ...
}
```

DB 컬럼은 `NUMBER`였다. Oracle의 `NUMBER`는 정밀도를 지정하지 않으면 38자리까지 담는다. 즉 **DB는 문제없이 저장하고 있었고, Java로 꺼내는 순간 잘렸다.**

기존 Flash 모듈이 이 값을 어떻게 다뤘는지는 확인하지 못했다. 다만 새로 만든 연동 경로에서만 증상이 나왔으므로, 기존 경로는 이 DTO를 타지 않았거나 다른 타입으로 받고 있었을 것으로 본다. 이건 추측이다.

## 무엇으로 바꿀 것인가

`long`으로 바꾸면 범위는 약 922경까지 늘어난다. 당장의 오버플로는 사라진다. 하지만 금액을 다루는 타입으로 `long`이 정답인지는 별개 문제다.

먼저 일반론을 정리한다. 금액 타입의 교과서적 답은 `BigDecimal`이고, 그 이유를 아래에 적는다. **그런데 이번에는 그 답을 고르지 않았다.** 왜 일반론과 다른 선택을 했는지가 이 글에서 쓰고 싶은 부분이다.

### long의 한계

`long`은 정수만 담는다. 원 단위 금액이라면 소수점이 없으니 괜찮아 보이지만, 다음 순간 문제가 된다.

- 세율이나 할인율을 곱하는 계산이 들어올 때
- 외화나 소수점 단위를 다루는 통화가 들어올 때
- 나눗셈이 필요할 때 (`long` 나눗셈은 소수점을 버린다)

### double은 후보가 아니다

부동소수점은 금액에 쓰면 안 된다. 십진 소수를 이진으로 정확히 표현할 수 없기 때문이다.

```java
System.out.println(0.1 + 0.2);        // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3); // false
```

합계를 반복해 더하면 오차가 쌓인다. 금액에서 이건 그냥 틀린 값이다.

### BigDecimal

정확한 십진 연산이 필요하면 `BigDecimal`이 맞다.

```java
public class ContractDto {
    private String contractNo;
    private BigDecimal amount;
    // ...
}
```

쓸 때 주의할 것이 두 가지 있다.

**생성자에 double을 넘기지 않는다.** 이미 오차가 낀 값을 그대로 받아 온다.

```java
new BigDecimal(0.1);      // 0.1000000000000000055511151231257827021181583404541015625
new BigDecimal("0.1");    // 0.1
BigDecimal.valueOf(0.1);  // 0.1  (내부에서 Double.toString을 거친다)
```

문자열 생성자나 `valueOf`를 쓴다.

**비교는 `equals`가 아니라 `compareTo`로 한다.** `equals`는 스케일까지 본다.

```java
new BigDecimal("1.0").equals(new BigDecimal("1.00"));      // false
new BigDecimal("1.0").compareTo(new BigDecimal("1.00"));   // 0 (같음)
```

`1.0`과 `1.00`은 값은 같고 스케일이 다르다. 금액 비교에서 `equals`를 쓰면 같은 금액이 다르다고 나온다.

### 실제로 고른 것

이번에는 `long`으로 갔다. 이유는 정확성보다 **연동 상대와의 계약**이었다.

이 금액은 다른 시스템과 주고받는 값이고, 그쪽은 정수 금액만 받는다. 소수점이 붙은 값이 넘어가면 그대로 오류다. 그래서 이 시스템의 금액 계산은 처음부터 정수로 나누어떨어지도록 되어 있었고, 소수가 생길 수 있는 타입을 쓰면 "생기지 않도록 검증하는" 코드가 따라와야 했다.

`long`을 쓰면 소수가 **타입 수준에서 존재할 수 없다.** 검증으로 막는 것이 아니라 구조로 막는다. 상한도 21억에서 922경으로 올라가 이번 오버플로는 사라진다.

`BigDecimal`이 금액 타입으로 더 일반적인 답이라는 것은 그대로다. 다만 이 시스템에서는 소수를 허용하는 것 자체가 잘못된 값이므로, 표현 폭이 넓은 타입이 오히려 틀린 선택이었다. 세율 계산이나 외화가 들어오는 순간 이 판단은 뒤집힌다. 그때는 `BigDecimal`로 가야 하고, 그 전환 비용은 지금 `long`으로 얻는 단순함과 맞바꾼 것이다.

한 가지는 그대로다. DTO를 처음 만들 당시에는 `int`로 충분했을 것이고, "지금은 안 넘는다"는 조건은 데이터가 쌓이면서 깨졌다. `long`도 같은 종류의 조건 위에 있다. 922경은 원 단위 금액에서 사실상 넘지 않는 값이라 받아들였을 뿐이다.

## 왜 검증에서야 발견됐는가

이 부분이 실은 가장 중요하다.

기존 화면과 새 화면을 나란히 놓고 값을 대조하지 않았다면 이 버그는 운영에 나갔을 것이다. 예외가 없으니 로그에 안 남고, 금액 하나가 틀린 것은 시스템 어디도 알려 주지 않는다.

레거시를 대체할 때 새 구현이 기능적으로 동작하는지를 확인하는 것만으로는 부족하다. **같은 입력에 같은 출력이 나오는지**를 데이터로 대조해야 한다. 새로 만든 쪽이 옳다는 보장이 없기 때문이다.

## 정리

- 뺄셈이 없는데 결과가 음수라면 오버플로를 먼저 의심한다.
- Java의 정수 연산은 범위를 넘어도 예외를 던지지 않는다. 조용히 부호가 뒤집힌다.
- `int`의 상한은 약 21억이다. 원 단위 금액에서는 충분히 넘길 수 있는 값이다.
- 금액에 `double`은 쓰지 않는다. 일반적으로는 `BigDecimal`을 쓰되 `double` 생성자를 피하고 비교는 `compareTo`로 한다.
- 다만 연동 상대가 정수만 받는다면 `long`이 맞을 수 있다. 소수가 존재할 수 없다는 것을 검증 코드가 아니라 타입으로 보장하는 편이 낫다.
- 타입은 DB 컬럼과 연동 상대의 표현 범위에 맞춰 정한다. "지금은 안 넘는다"는 조건에 기대면 시한부다.
- 레거시 대체는 기능 동작 확인이 아니라 기존 결과와의 값 대조로 검증한다.

Java에서 `Math.addExact` 같은 메서드는 오버플로 시 `ArithmeticException`을 던진다. 조용히 틀리는 것보다 터지는 편이 나은 계산에는 이쪽을 쓸 수 있다. 다만 이번 건에는 적용하지 않았다.
