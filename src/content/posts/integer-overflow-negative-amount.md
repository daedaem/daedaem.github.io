> 코드와 테이블명은 문제의 구조를 보여주기 위해 일반적인 형태로 옮긴 것이다. 실제 시스템의 코드가 아니다.

동료와 함께 지원이 끝난 Flash 기반 계약 모듈을 외부 서비스 연동으로 바꾸는 작업을 진행했다. 테스트 중 **일부 건의 금액이 음수로 표기되는 것을 발견했다.** 실제로는 큰 양수여야 할 값이었다.

문제가 된 금액 처리는 이미 구현되어 있던 부분이었다. 이 글은 테스트에서 발견한 문제를 확인하고 수정한 기록이다. 맡은 범위와 전환 과정은 [따로 적었다](/posts/retire-flash-module-by-integration/).

## 음수는 어디서 오는가

이 경로에는 뺄셈이 없었다. 대부분의 건은 정상이고 금액이 큰 특정 건에서만 부호가 뒤집혀, 먼저 금액을 담는 타입의 표현 범위를 의심했다. 음수라는 증상만으로 변환 방식을 단정하지 않고 DB 값과 VO 값을 대조했다.

## VO의 필드 타입

금액이 담기는 자리는 MyBatis 조회 결과를 받는 VO였다. 다음은 필드 구성을 단순화한 예시다.

```java
// MyBatis 매퍼의 resultType으로 쓰인다
public class ContractVo {
    private String contractNo;
    private int amount;        // 금액을 받는 필드
    // ...
}
```

DB 컬럼은 `NUMBER`였다. Oracle의 `NUMBER`는 십진 유효숫자 최대 38자리의 정밀도를 지원한다. DB 값과 VO의 값을 대조하니 **DB 금액은 정상이었지만 VO의 `int` 필드에는 음수가 담겨 있었다.**

> VO의 금액 필드를 `int`에서 `long`으로 변경한 뒤 정상값이 표시되는 것을 확인했다.

이 사례에서 확인한 흐름은 DB의 정상 금액, VO에서의 음수 표시, 그리고 필드 타입 변경 뒤의 정상 표시다. 기존 Flash 모듈이 이 값을 어떻게 다뤘는지는 확인하지 못했다.

## 학습 예시 — 큰 정수를 int로 좁히면

다음은 타입의 표현 범위와 명시적 형 변환을 설명하는 예시다. 앞의 DB·VO 대조 결과와 구분해서 본다.

Java의 `int`는 32비트 부호 있는 정수다. 표현 범위는 다음과 같다.

```
Integer.MIN_VALUE = -2,147,483,648
Integer.MAX_VALUE =  2,147,483,647
```

약 21억이다. 원 단위 금액에서 21억은 큰 수가 아니다. 계약 금액이나 누적 합계라면 어렵지 않게 넘는다.

예를 들어 계약 금액이 30억 원이라고 가정해 보자. 이 값을 `long`에 담은 뒤 `int`로 강제 변환하면 다음과 같다.

```java
long amount = 3_000_000_000L;  // 정상 금액: 30억 원
int wrong = (int) amount;
System.out.println(wrong);     // -1294967296
```

`long`에서 `int`로 좁히는 변환은 하위 32비트만 남긴다. 3,000,000,000은 `int`의 양수 범위를 넘고, 남은 비트를 부호 있는 정수로 해석하면 -1,294,967,296이 된다. 이 변환은 예외를 던지지 않지만, 범위를 넘은 모든 값이 음수가 되는 것은 아니다.

> 표지와 코드의 30억 원은 원리를 설명하기 위한 가상 금액이며, 실제 당시 계약 금액이 아니다. 이 코드는 Java의 명시적 형 변환 예제이며, 실제 DB→VO 경로에서 같은 변환이 일어났다는 재현 결과는 아니다.

명시적 `(int)` 변환과 JDBC로 DB 값을 읽는 과정은 같은 동작이라고 가정할 수 없다. DB→VO 경로의 변환을 설명하려면 JDBC에서 값을 읽는 방식, MyBatis 매핑과 중간 변환을 함께 확인해야 한다. 위 예시만으로 'Oracle NUMBER를 int로 읽으면 항상 이런 음수가 된다'고 일반화하지 않는다.

Java의 일반적인 정수 덧셈·곱셈도 오버플로 자체를 예외로 알리지 않는다. 표현 범위를 넘은 결과가 양수로 남을 수도 있으므로 부호만 보는 검증은 충분하지 않다. 계산 결과가 필요한 범위에 들어오는지와 기대한 값에 일치하는지를 확인해야 한다.

Java에서 `Math.addExact` 같은 메서드는 덧셈 오버플로 시 `ArithmeticException`을 던진다. 이런 검사는 계산에서 범위 초과를 감지하는 수단이며, 이번 VO 필드 변경에 적용한 것은 아니다.

## 무엇으로 바꿀 것인가

`long`의 양수 상한은 약 922경이다. 이번에는 필요한 금액 범위를 담을 수 있었지만, 모든 금액 처리에 `long`이 적합하다는 뜻은 아니다.

정확한 십진 연산이 필요하면 `BigDecimal`이 적합하다. 반면 최소 화폐 단위의 정수로 저장하고 범위와 반올림 규칙을 관리한다면 `long`도 유효한 선택이다.

### long의 한계

`long`은 정수만 담는다. 다음 요구가 생기면 금액의 단위, 중간 계산의 타입과 반올림 시점을 함께 정해야 한다.

- 세율이나 할인율을 곱하는 계산이 들어올 때
- 외화나 소수점 단위를 다루는 통화가 들어올 때 (센트 같은 최소 단위의 정수로 표현할 수도 있다)
- 나눗셈이 필요할 때 (`long` 나눗셈은 소수점을 버린다)

### double은 후보가 아니다

십진 금액을 정확히 보존해야 하는 이 용도에는 `double`을 쓰지 않는다. `0.1`처럼 이진 부동소수점으로 정확히 표현할 수 없는 십진 소수가 있기 때문이다.

```java
System.out.println(0.1 + 0.2);        // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3); // false
```

합계를 반복해 더하면 표현 오차가 누적될 수 있다. 정확한 금액과 정해진 반올림 규칙을 지켜야 하는 계산에는 적합하지 않다.

### BigDecimal

정확한 십진 연산이 필요하면 `BigDecimal`이 맞다.

```java
public class ContractVo {
    private String contractNo;
    private BigDecimal amount;
    // ...
}
```

쓸 때 주의할 것이 두 가지 있다.

**생성자에 double을 넘기지 않는다.** 이미 오차가 낀 값을 그대로 받아 온다.

```java
new BigDecimal(0.1);      // 0.1000000000000000055511151231257827021181583404541015625
new BigDecimal("0.1");    // 0.1
BigDecimal.valueOf(0.1);  // 0.1  (내부에서 Double.toString을 거친다)
```

문자열 생성자나 `valueOf`를 쓴다.

**수치가 같은지 비교할 때는 `compareTo`를 쓴다.** `equals`는 스케일까지 비교하므로 값과 스케일을 모두 구분하려는 경우에 쓴다.

```java
new BigDecimal("1.0").equals(new BigDecimal("1.00"));      // false
new BigDecimal("1.0").compareTo(new BigDecimal("1.00"));   // 0 (같음)
```

`1.0`과 `1.00`은 값은 같고 스케일이 다르다. 금액 비교에서 `equals`를 쓰면 같은 금액이 다르다고 나온다.

### 실제로 고른 것

이번에는 `long`으로 갔다. **연동 상대가 정수 금액만 받는 계약**과 필요한 표현 범위에 맞춘 선택이었다.

이 VO는 다른 시스템에 전달할 정수 금액을 담는 용도였고, 이번에 필요한 범위가 `long` 안에 들어왔다. 정수 전달이라는 계약과 표현 범위를 함께 고려해 필드 타입을 선택했다.

`long` 필드에는 소수 부분을 저장할 수 없다. 다만 이것은 잘못된 소수 입력을 자동으로 거부한다는 뜻이 아니다. 형 변환이나 정수 나눗셈에서 소수 부분이 버려질 수 있으므로, 입력값과 중간 계산의 정확성은 별도로 검증해야 한다.

`BigDecimal`로도 스케일과 정수 변환을 검증하면 같은 계약을 지킬 수 있으므로 틀린 선택인 것은 아니다. 이번에는 정수 필드의 단순함을 택했다. 소수 계산이 추가되면 중간 계산의 타입과 반올림 시점을 다시 정해야 한다. `long`이라고 해서 나눗셈의 절삭이나 오버플로까지 막히지는 않는다.

이 VO를 처음 만들 때 어떤 상한을 가정했는지는 확인하지 못했다. 다만 현재 데이터가 타입의 범위에 들어오는지는 별도로 검증해야 한다. `long`도 유한한 타입이므로, 이번에 필요한 범위를 만족한다는 판단과 앞으로도 절대 넘지 않는다는 보장은 구분한다.

## 테스트에서 확인한 것

이번 문제는 동료와 함께 개발하던 중 테스트에서 발견했다. 금액이 표시되는지만 확인했다면 정상 동작으로 지나칠 수 있었지만, 실제 값이 맞는지 확인하면서 기존 금액 처리의 문제를 찾았다.

레거시를 대체할 때 기능이 동작하는지만 확인하는 것으로는 부족하다. 기존 코드를 사용하는 부분도 **기대하는 금액과 실제 표시 금액이 같은지** 확인해야 한다.

## 정리

- 큰 금액에서 음수가 보이면 표현 범위를 의심하되, DB 값과 애플리케이션 값을 대조한다. 명시적 형 변환 예제를 실제 JDBC 변환 경로의 증거로 쓰지는 않는다.
- 이번에는 DB·VO 값을 대조하고 `int` 필드를 `long`으로 바꿔 정상 표시를 확인했다. 최초 필드 설계의 상한이나 기존 Flash 모듈의 처리 방식까지 설명하는 것은 아니다.
- 정확한 십진 연산에는 `BigDecimal`을, 최소 단위의 정수 금액에는 범위를 확인한 뒤 `long`을 고려한다. `long`도 절삭과 오버플로 검증이 필요하다.
- 레거시 전환 검증에서는 기능 동작뿐 아니라 기대한 금액과 실제 결과도 대조한다.

**보충(2026-10-26):** DB·VO 대조와 타입 변경 결과를 먼저 설명하고, 명시적 형 변환 예시를 별도 절로 분리했다. `long`이 소수 입력의 오류나 계산의 정확성까지 보장한다는 오해가 없도록 타입 선택 기준을 보완했다.
