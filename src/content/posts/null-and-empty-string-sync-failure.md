> 회사·고객을 식별할 수 있는 정보, 실제 업무 데이터, 내부 코드와 구분값은 공개하지 않는다.

업무 시스템은 SAP MDM(기준 정보를 관리하는 시스템)과 데이터를 주고받았다. 업무 시스템에서 변경한 정보를 MDM에 반영하려면 결재가 필요했다. 문제는 이미 처리한 변경인데도 결재가 다시 올라오는 것이었다. 동기화가 필요하지 않은데도 반복되는 결재였고, 오류 지점을 특정하기 어려워 5년 넘게 남아 있던 문제였다.

정보가 들어오는 경로는 두 가지였다. MDM에서 직접 등록·수정한 정보가 업무 시스템으로 내려오기도 했고, 업무 시스템에서 등록·변경한 정보가 MDM에 반영된 뒤 다시 내려오기도 했다. 따라서 반복 결재라는 증상만으로는 보내는 데이터, MDM의 반영, 업무 시스템의 수신 처리 중 어디가 잘못됐는지 구분하기 어려웠다.

## 화면부터 수신 프로시저까지 따라갔다

관련 로직은 화면, Spring 서비스, Oracle 프로시저, 인터페이스에 나뉘어 있었다. 한 지점만 봐서는 잘못된 변경 판단이 어디에서 생기는지 알기 어려웠다. 관련 데이터와 각 계층의 비교·반영 로직을 따라가며 원인을 조사했다.

같은 반복 결재로 보였지만 원인은 두 가지였다. 하나는 NULL과 빈 문자열을 다루는 비교 오류였고, 다른 하나는 MDM에서 내려오는 데이터의 구분값과 업무 시스템의 처리 대상 선택 기준이 맞지 않는 문제였다. 두 오류를 분리해 각각 수정했다.

## 원인 1 — NULL과 빈 문자열 비교 오류

Oracle은 길이가 0인 문자열을 `NULL`로 취급한다. 여기서 빈 문자열은 `''`이며 공백 문자가 들어 있는 `' '`와는 다르다. [Oracle의 NULL 설명](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Nulls.html)

수신 데이터의 빈 값과 DB에 저장된 값을 다루는 방식이 맞지 않았고, Java의 `equals`를 사용하는 비교 부분에서 문제가 있었다. 빈 값의 표현 차이를 실제 변경으로 판단하지 않도록, 송신 측 데이터 규격에 맞게 NULL·빈 문자열 비교 로직을 수정했다.

아래는 Oracle의 동작을 설명하는 학습 예시다. 당시 운영 SQL이나 수정 전후의 코드를 재현한 것은 아니다.

```sql
SELECT CASE WHEN '' IS NULL THEN 'NULL' ELSE 'VALUE' END AS empty_value
  FROM dual;
-- 결과: 'NULL' (NULL 값이 아니라 문자열)
```

빈 값의 저장·비교 원리는 [Oracle 빈 문자열과 NULL](/wiki/oracle-empty-string-is-null/)에 따로 정리했다. 일반적인 처리 방법과 이번에 실제 수행한 수정은 구분해서 읽어야 한다.

## 원인 2 — MDM 수신 데이터의 구분 기준 문제

빈 값 비교를 수정한 뒤 증상이 일부 개선됐지만, 현업에서 변경하지 않은 정보가 다시 변경으로 감지된다는 제보를 받았다. 다시 확인해 보니 최신 값으로 변경한 특정 항목이 MDM에서 내려온 데이터에는 이전 값으로 남아 있었다.

해당 사례의 데이터를 추출해 항목별로 대조하면서, 어떤 항목이 최신 값으로 반영되지 않는지 확인했다. 관련 데이터와 코드·프로시저를 함께 살펴보니, 내려온 여러 행 중 처리할 행을 구분하는 값과 그 값을 확인하는 조건이 의심됐다.

SAP 담당자에게 어떤 행을 처리해야 하는지와 이를 구분하는 기준을 확인했다. 그 기준으로 수신 데이터를 다시 살펴본 결과, 기대한 구분값이 정상적으로 표시되어 내려오지 않는 문제를 발견했다. 담당자와 기준을 맞춘 뒤 SAP 측 데이터와 업무 시스템 측 처리에 각각 필요한 수정을 반영했다.

빈 값 비교 오류와 수신 데이터의 구분 기준 문제는 같은 반복 결재 증상을 만들었지만 원인과 수정 지점이 달랐다. 첫 번째 수정 뒤에도 남은 증상을 데이터 대조와 담당자 확인으로 추적해 두 번째 원인을 찾아냈다.

## 결과와 남긴 기준

NULL·빈 문자열 비교 로직과 MDM 수신 데이터의 구분값·처리 대상 선택 기준을 바로잡아, 동기화가 필요하지 않은데도 반복되던 결재를 없앴다. 동기화를 위한 정상적인 결재 절차는 유지했다.

수정 대상에 대해 개별 변경, 복수 변경, 미변경 사례를 사용자 화면에서 수동으로 실행했다. 변경 여부에 따른 처리 결과가 기대와 일치하는지 확인했다.

이 작업의 핵심은 두 입력 경로와 여러 계층에 흩어진 로직을 따라가며, 같은 증상을 만드는 서로 다른 원인을 구분한 데 있었다. 항목별 데이터 대조로 의심 범위를 좁히고, SAP 담당자에게 확인한 기준을 실제 수신 데이터와 비교해 수정 근거를 확보했다.

- 빈 값 비교와 수신값 반영을 별개의 확인 지점으로 본다.
- 인터페이스는 컬럼이 존재하는지만이 아니라 각 값의 의미와 수신 측 분기 조건까지 맞아야 한다.
- 같은 증상이 남아 있다고 해서 수정한 원인 하나만 다시 볼 것이 아니라, 다른 경로의 오류도 구분해서 확인한다.
