> 코드와 테이블명은 문제의 구조를 보여주기 위해 일반적인 형태로 옮긴 것이다. 실제 시스템의 코드가 아니다.

두 시스템 사이에서 데이터가 어긋나는 문제가 있었다. 한쪽에서 값을 바꿔 결재를 거쳐 상대 시스템에 보내면, 상대 시스템에서 내려온 값이 다시 반영되어야 하는 양방향 구조였다. 그런데 내려온 값이 반영되지 않는 건이 간헐적으로 나왔고, 그러면 같은 변경이 다시 감지되어 **이미 처리한 건에 대한 결재가 또 올라갔다.** 이런 불필요한 결재가 월 34건씩 반복되고 있었다. 오래된 문제였고, 그동안은 발견될 때마다 사람이 손으로 맞추는 방식으로 넘어가고 있었다.

간헐적이라는 점이 이 문제를 오래 살려 둔 이유였다. 재현이 안 되니 원인을 잡을 수 없고, 원인을 모르니 수기 보정 말고는 방법이 없었다.

조사 끝에 나온 것은 **서로 아무 관계 없는 원인 두 건**이었다.

## 왜 간헐적으로 보였는가

두 개의 독립적인 원인이 하나의 증상으로 보일 때, 증상은 반드시 불규칙해 보인다.

원인 A만 있을 때, 원인 B만 있을 때, 둘 다 있을 때가 섞여서 나타나기 때문이다. "이럴 때 재현된다"는 조건을 하나로 만들려는 시도는 애초에 성립할 수 없었다. 조건을 찾지 못한 게 아니라 조건이 하나가 아니었던 것이다.

그래서 재현 조건을 찾는 방향을 접고, 데이터가 지나가는 경로를 처음부터 끝까지 따라가며 각 구간에서 값이 무엇인지 확인하는 방식으로 바꿨다. 화면, 서비스, 매퍼, 쿼리, 인터페이스 테이블, 수신 측 순으로 훑었다.

## 원인 1 — 계층마다 다른 NULL 비교

변경 여부를 판정하는 비교가 한 곳이 아니었다. 화면에서 넘어온 값과 저장된 값을 견주는 Java 코드가 있었고, 인터페이스 테이블에서 이전 값과 새 값을 견주는 SQL이 따로 있었다. 둘은 같은 질문("값이 바뀌었는가")에 답하는데, `null`과 `""`가 끼면 서로 다른 답을 냈다.

### Java 쪽

Java 코드의 비교는 대략 이런 모양이었다.

```java
// 이전 값과 새 값이 다르면 변경 대상으로 표시한다
if (!oldValue.equals(newValue)) {
    markAsChanged(column);
}
```

`oldValue`가 `null`이면 `equals` 호출 자체가 `NullPointerException`이다. 그래서 앞에 방어가 들어가 있었다.

```java
// null을 빈 문자열로 바꿔서 비교한다
String oldSafe = oldValue == null ? "" : oldValue;
String newSafe = newValue == null ? "" : newValue;

if (!oldSafe.equals(newSafe)) {
    markAsChanged(column);
}
```

NPE는 막았다. 대신 이 코드 기준으로 `null`과 `""`는 같은 값이다. `null`이었던 컬럼에 `""`가 들어와도 "변경 없음"이다. 이 판정 자체가 틀렸다고는 할 수 없다. 문제는 다른 계층이 같은 두 값을 다르게 판정했다는 데 있다.

### Oracle 쪽

**Oracle은 빈 문자열을 NULL로 저장한다.** 다른 DBMS와 다른 Oracle 고유의 동작이다.

```sql
-- Oracle에서는 둘 다 NULL이 들어간다
INSERT INTO t (col) VALUES ('');
INSERT INTO t (col) VALUES (NULL);

SELECT CASE WHEN '' IS NULL THEN 'NULL이다' ELSE '아니다' END FROM dual;
-- 결과: NULL이다
```

그래서 애플리케이션이 `""`를 보냈든 `null`을 보냈든 테이블에는 구분 없이 `NULL`이 남는다. Java 쪽에서 둘을 구분해 봐야 DB를 거치면 다시 합쳐진다.

그리고 SQL의 NULL 비교는 `=`나 `<>`로 되지 않는다. 이건 Oracle만의 얘기가 아니라 SQL 표준이다.

```sql
-- 한쪽이 NULL이면 이 조건은 참도 거짓도 아닌 UNKNOWN이 되어 그 행이 빠진다
WHERE old_col <> new_col

-- NULL을 값의 하나로 취급해 비교하는 형태
WHERE (old_col IS NULL AND new_col IS NOT NULL)
   OR (old_col IS NOT NULL AND new_col IS NULL)
   OR old_col <> new_col
```

인터페이스 테이블 쪽 SQL은 `<>` 하나로 비교하고 있었다. 한쪽이 NULL이고 다른 쪽이 값이면 `old <> new`는 UNKNOWN이 되고, WHERE 절에서 UNKNOWN은 거짓처럼 취급되어 그 행이 결과에서 빠진다.

같은 두 값을 두고 Java는 "같다"고 하고, SQL은 판정을 포기하고 행을 버렸다. 값이 어느 경로로 들어왔고 어느 비교를 먼저 거쳤는지에 따라 같은 건이 변경으로 잡히기도, 빠지기도 했다. 간헐적으로 보인 이유의 절반이 여기 있었다.

### 고친 방향

`null`과 `""`를 어떻게 볼 것인가보다 먼저 정한 것은 **비교 지점을 하나로 모으는 것**이었다. SQL 쪽 비교를 걷어 내고, 변경 여부는 애플리케이션의 한 메서드에서만 판정하게 했다. 그 메서드 안에서 두 값을 경계에서 하나로 정규화한다. 정규화 기준은 상대 시스템이 빈 값을 보내는 규격에 맞췼다. 비교 대상의 절반은 상대가 보낸 값이니, 그쪽 규격이 기준이 되어야 양쪽 판정이 같아진다.

```java
/**
 * 비교 이전에 값을 정규화한다.
 * Oracle이 빈 문자열을 NULL로 저장하는 이상, 애플리케이션에서 둘을 구분해 봐야
 * DB를 거치면서 다시 합쳐진다. 그래서 구분하는 대신 한쪽으로 모은다.
 */
private static String normalize(String value) {
    return (value == null || value.isEmpty()) ? null : value;
}

private boolean changed(String oldValue, String newValue) {
    return !Objects.equals(normalize(oldValue), normalize(newValue));
}
```

`Objects.equals`는 양쪽이 `null`이면 `true`, 한쪽만 `null`이면 `false`를 돌려준다. NPE 방어와 비교를 한 줄에서 해결한다.

이 메서드 하나만 놓고 보면 `null`과 `""`를 같게 보는 규칙은 기존 방어 코드와 다르지 않다. 달라진 것은 규칙이 아니라 **규칙이 적용되는 곳이 하나가 됐다**는 점이다. 어떤 경로로 값이 들어와도 같은 판정이 나오니, "여기서는 같고 저기서는 빠지는" 상태가 사라졌다. 세 갈래 SQL로 고치는 방법도 있었지만 비교 지점이 둘로 남는 것은 그대로라 택하지 않았다.

## 원인 2 — 누구의 값인지 정하지 않은 항목

두 번째는 성격이 완전히 달랐다. 비교 로직이 아니라 **데이터 소유권** 문제였다.

두 시스템은 같은 업체 정보를 양쪽에서 고칠 수 있는 구조였다. 그런데 항목 중 일부는 상대 시스템이 원본을 관리하는, 즉 상대가 주인인 항목이었다. 우리 쪽 변경 감지는 그 구분 없이 모든 항목을 비교 대상에 넣고 있었다.

여기에 한 가지가 더 겹쳤다. 어떤 항목은 한 업체에 값이 여럿일 수 있는데(연락처가 대표적이다), 그중 어느 것이 대표값인지는 인터페이스에 실려 오는 플래그가 정한다. 이 플래그의 규격이 5년 이상 전에 바뀌었는데, 우리 쪽 반영 로직은 옛 규격 그대로였다. 상대는 자기 기준의 대표값을 보내고 우리는 우리 기준의 값을 들고 있으니, 아무도 손대지 않아도 두 값은 계속 "다르다"고 비교됐다. 그 결과 변경이 없는 건이 변경 대상으로 잡혀 결재가 다시 올라갔다. 규격이 바뀔 때 어느 쪽에서 전달이 끊겼는지는 기록이 남아 있지 않아 알 수 없었고, 그걸 따지는 것은 문제를 고치는 데 필요하지도 않았다.

원인 1과 같은 증상으로 보였을 뿐 접점이 전혀 없었다. 여기서 두 원인을 분리해 본 것이 중요했다. 하나를 고치고 나서 증상이 여전히 남으면 "고친 게 잘못됐나" 하고 되돌아가기 쉬운데, 둘이 별개임을 먼저 확인해 두면 그럴 일이 없다.

### 고친 방향

항목별로 **어느 시스템이 주인인지를 먼저 정했다.** 상대가 주인인 항목은 우리 쪽 변경 감지와 반영 대상에서 뺐다. 우리가 바꿔 봐야 상대가 다시 덮어쓸 값이고, 상대가 보낸 값과 비교해 봐야 의미가 없다. 값이 여럿일 수 있는 항목은 상대가 보내는 대표값 플래그를 현재 규격대로 반영하게 고쳐 비교 대상을 하나로 고정했다.

인터페이스 테이블과 프로시저를 그에 맞게 고쳤고, 상대 시스템 담당자와 항목별 소유권 표를 합의하는 데 코드 수정보다 시간이 더 들었다. 어느 항목을 뺄지는 코드가 아니라 업무의 문제였기 때문이다.

일반화하면 이렇다. **두 시스템이 같은 데이터를 양방향으로 주고받을 때, 항목마다 주인이 하나로 정해져 있지 않으면 변경 감지는 성립하지 않는다.** 비교 코드를 아무리 잘 짜도 "무엇과 무엇을 비교하는가"가 정의되지 않은 상태이기 때문이다.

## 정리

- 증상이 불규칙하면 원인이 하나가 아닐 수 있다. 재현 조건을 찾기 전에 원인이 몇 개인지부터 의심하는 편이 빨랐다.
- Oracle은 빈 문자열을 NULL로 저장하고, SQL에서 `NULL <> value`는 UNKNOWN이라 WHERE 절에서 걸러진다. Java의 null→"" 방어와 만나면 같은 두 값이 계층마다 다르게 판정된다.
- 변경 판정은 한 지점에서만 한다. 정규화 규칙 자체보다 그 규칙이 적용되는 곳이 하나라는 것이 중요했다.
- 양방향 동기화에서는 항목마다 주인이 하나여야 한다. 인터페이스 규격이 바뀌면 양쪽이 같이 바뀌었는지 확인할 수단이 있어야 하고, 없으면 한쪽만 바뀐 상태가 몇 년씩 간다.

5년 넘게 남아 있던 문제였지만 원인 자체는 어렵지 않았다. 어려웠던 것은 두 개의 원인이 하나의 증상으로 겹쳐 보이는 상황에서 그걸 갈라 놓는 일이었다.
