> 코드와 테이블명은 문제의 구조를 보여주기 위해 일반적인 형태로 옮긴 것이다. 실제 시스템의 코드가 아니다.

두 시스템 사이에서 데이터가 어긋나는 문제가 있었다. 한쪽에서 값을 바꿔도 다른 쪽에 반영되지 않는 건이 간헐적으로 나왔다. 오래된 문제였고, 그동안은 발견될 때마다 사람이 손으로 맞추는 방식으로 넘어가고 있었다.

간헐적이라는 점이 이 문제를 오래 살려 둔 이유였다. 재현이 안 되니 원인을 잡을 수 없고, 원인을 모르니 수기 보정 말고는 방법이 없었다.

조사 끝에 나온 것은 **서로 아무 관계 없는 원인 두 건**이었다. 이 글은 그 둘을 분리해 낸 과정과, 각각이 왜 발생했는지에 대한 기록이다.

## 왜 간헐적으로 보였는가

먼저 짚어 둘 것이 있다. 두 개의 독립적인 원인이 하나의 증상으로 보일 때, 증상은 반드시 불규칙해 보인다.

원인 A만 있을 때, 원인 B만 있을 때, 둘 다 있을 때가 섞여서 나타나기 때문이다. "이럴 때 재현된다"는 조건을 하나로 만들려는 시도는 애초에 성립할 수 없었다. 조건을 찾지 못한 게 아니라 조건이 하나가 아니었던 것이다.

그래서 재현 조건을 찾는 방향을 접고, 데이터가 지나가는 경로를 처음부터 끝까지 따라가며 각 구간에서 값이 무엇인지 확인하는 방식으로 바꿨다. 화면, 서비스, 매퍼, 쿼리, 인터페이스 테이블, 수신 측 순으로 훑었다.

## 원인 1 — NULL과 빈 문자열

변경 여부를 판정하는 로직이 있었다. 대략 이런 모양이었다.

```java
// 이전 값과 새 값이 다르면 변경 대상으로 표시한다
if (!oldValue.equals(newValue)) {
    markAsChanged(column);
}
```

여기서 값이 하나는 `null`이고 하나는 `""`인 경우가 있었다.

### Java 쪽 문제

`null`과 `""`는 Java에서 명백히 다른 값이다. 문제는 그 앞에 있었다. `oldValue`가 `null`이면 `equals` 호출 자체가 `NullPointerException`이다. 그래서 코드 어딘가에는 방어가 들어가 있었고, 그 방어가 이렇게 생겼다.

```java
// null을 빈 문자열로 바꿔서 비교한다
String oldSafe = oldValue == null ? "" : oldValue;
String newSafe = newValue == null ? "" : newValue;

if (!oldSafe.equals(newSafe)) {
    markAsChanged(column);
}
```

NPE는 막았다. 대신 **`null`과 `""`를 같은 값으로 만들어 버렸다.** `null`이었던 컬럼에 `""`가 들어와도 "변경 없음"으로 판정되어 동기화 대상에서 빠진다.

방어 코드가 버그를 만든 전형적인 경우다. `null`을 안전하게 처리한 것이 아니라, `null`이라는 정보를 지운 것이었다.

### Oracle 쪽 문제

같은 혼동이 DB에도 있었다. **Oracle은 빈 문자열을 NULL로 저장한다.** 다른 DBMS와 다른 Oracle 고유의 동작이다.

```sql
-- Oracle에서는 둘 다 NULL이 들어간다
INSERT INTO t (col) VALUES ('');
INSERT INTO t (col) VALUES (NULL);

SELECT CASE WHEN '' IS NULL THEN 'NULL이다' ELSE '아니다' END FROM dual;
-- 결과: NULL이다
```

그래서 애플리케이션이 `""`를 보냈든 `null`을 보냈든 테이블에는 구분 없이 `NULL`이 남는다. Java 쪽에서 둘을 구분해 고쳐 봐야 DB를 거치면 다시 합쳐진다.

그리고 NULL 비교는 `=`로 하면 안 된다. 이건 Oracle만의 얘기가 아니라 SQL 표준이다.

```sql
-- 이 조건은 영원히 참이 되지 않는다. NULL = NULL 은 참이 아니라 UNKNOWN이다
WHERE old_col <> new_col

-- 의도한 대로 동작하는 형태
WHERE (old_col IS NULL AND new_col IS NOT NULL)
   OR (old_col IS NOT NULL AND new_col IS NULL)
   OR old_col <> new_col
```

`<>` 하나로 끝날 것 같은 비교가 NULL이 끼면 세 갈래가 된다. 한쪽이 NULL이고 다른 쪽이 값인 경우 `old <> new`는 참이 아니라 UNKNOWN이 되고, WHERE 절에서 UNKNOWN은 거짓처럼 취급되어 그 행이 빠진다.

Oracle 12c 이상이면 `DECODE`나 `NVL`보다 이 형태가 명시적이라 낫다고 본다. 다만 운영 환경이 10g였기 때문에 사용할 수 있는 문법에 제약이 있었고, 최종적으로는 비교 자체를 애플리케이션 계층에서 명시적으로 하도록 옮겼다.

### 고친 방향

`null`과 `""`를 구분해서 다루려 하지 않고, **경계에서 하나로 정규화**하는 쪽을 골랐다.

```java
/**
 * 비교 이전에 값을 정규화한다.
 * Oracle이 빈 문자열을 NULL로 저장하는 이상, 애플리케이션에서 둘을 구분해 봐야
 * DB를 거치면서 다시 합쳐진다. 그래서 구분하는 대신 한쪽으로 모은다.
 */
private static String normalize(String value) {
    return (value == null || value.isEmpty()) ? null : value;
}

private boolean changed(String oldValue, String newValue) {
    return !Objects.equals(normalize(oldValue), normalize(newValue));
}
```

`Objects.equals`는 양쪽이 `null`이면 `true`, 한쪽만 `null`이면 `false`를 돌려준다. NPE 방어와 비교를 동시에 해결한다.

핵심은 `Objects.equals`를 쓴 것보다 **정규화 지점을 하나로 정한 것**이다. 값이 시스템에 들어오는 경계에서 한 번만 정규화하면, 그 안쪽 코드는 `""`를 신경 쓰지 않아도 된다.

## 원인 2 — 반영되지 않는 인터페이스 플래그

두 번째는 성격이 완전히 달랐다.

시스템 간 연동은 인터페이스 테이블을 경유했다. 송신 측이 행을 쌓고 처리 상태 플래그를 남기면, 수신 측이 미처리 건을 읽어 가는 구조다.

플래그가 갱신되지 않는 경로가 있었다. 그래서 이미 처리한 건이 미처리로 남거나, 반대로 처리되지 않은 건이 처리 완료로 넘어갔다.

이건 비교 로직 문제가 아니라 상태 전이 문제다. 원인 1과 같은 증상으로 보였을 뿐 접점이 전혀 없었다. 여기서 두 원인을 분리해 본 것이 중요했다. 하나를 고치고 나서 증상이 여전히 남으면 "고친 게 잘못됐나" 하고 되돌아가기 쉬운데, 둘이 별개임을 먼저 확인해 두면 그럴 일이 없다.

플래그가 갱신되지 않는 구체적인 경로와 조건은 시스템 구조를 특정할 수 있어 적지 않는다. 다만 일반화할 수 있는 부분은 이렇다. **처리 상태를 플래그 컬럼 하나로 표현하면, 그 컬럼을 갱신하지 못하는 경로가 하나라도 있을 때 상태가 조용히 어긋난다.** 실패했다는 사실 자체가 어디에도 남지 않기 때문이다.

이 구조에서는 상태 전이를 기록으로 남기는 편이 안전하다. 상태를 덮어쓰는 대신 전이 이력을 쌓으면, 갱신에 실패했을 때 마지막 상태가 언제 어떤 경로로 찍혔는지 되짚을 수 있다. 다만 이건 이번 작업에서 실제로 적용한 것이 아니라 조사하면서 든 판단이라, 추측으로 표시해 둔다.

## 정리

- 증상이 불규칙해 보이면 원인이 하나가 아닐 수 있다. 재현 조건을 찾기 전에 원인이 몇 개인지부터 의심하는 편이 빨랐다.
- `null`을 `""`로 바꿔 NPE를 막는 방어는 정보를 지운다. NPE는 사라지지만 두 값이 같아진다.
- Oracle은 빈 문자열을 NULL로 저장한다. 애플리케이션에서 둘을 구분해도 DB를 거치면 합쳐진다.
- SQL에서 `NULL <> value`는 참이 아니라 UNKNOWN이고, WHERE 절에서는 거짓처럼 걸러진다.
- 구분하려 애쓰기보다 경계에서 한쪽으로 정규화하는 편이 유지하기 쉬웠다.

수년간 남아 있던 문제였지만 원인 자체는 어렵지 않았다. 어려웠던 것은 두 개의 원인이 하나의 증상으로 겹쳐 보이는 상황에서 그걸 갈라 놓는 일이었다.
