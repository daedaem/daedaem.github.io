> **정정(2026-09-14):** 이전 글에 포함됐던 확인되지 않은 원인과 수행 설명을 삭제하고, 실제 수정 내용으로 다시 정리했다. 회사와 시스템을 특정하는 정보, 실제 코드와 처리 구분값은 공개하지 않는다.

업체정보를 주고받는 두 시스템 사이에서 수신값이 정상 반영되지 않는 문제가 있었다. 담당자가 원본 시스템에서 직접 수정한 값이 내려오는 경로와, 업무 시스템에서 요청한 변경을 원본 시스템에 반영한 뒤 다시 수신하는 경로가 있었다.

내려온 값이 반영되지 않으면 같은 변경이 다시 감지됐다. 이미 처리한 변경 때문에 결재가 다시 올라왔고, 불필요한 결재가 월 34건 발생했다. 오류 지점을 특정하기 어려워 5년 이상 남아 있던 문제였다.

## 화면부터 수신 프로시저까지 따라갔다

관련 로직은 화면, Spring 서비스, Oracle 프로시저, 인터페이스에 나뉘어 있었다. 한 지점만 봐서는 수신된 값이 어디에서 반영되지 않는지 알기 어려웠다. 데이터가 지나가는 각 계층의 비교·반영 로직을 전수 조사했다.

같은 반복 결재로 보였지만 원인은 두 가지였다. 하나는 NULL과 빈 문자열을 다루는 비교 오류였고, 다른 하나는 인터페이스의 처리 구분값이 수신 측 로직과 맞지 않는 문제였다. 두 오류를 분리해 각각 수정했다.

## 원인 1 — NULL과 빈 문자열 비교 오류

Oracle은 길이가 0인 문자열을 `NULL`로 취급한다. 여기서 빈 문자열은 `''`이며 공백 문자가 들어 있는 `' '`와는 다르다. [Oracle의 NULL 설명](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Nulls.html)

수신 데이터의 빈 값과 DB에 저장된 값을 다루는 방식이 맞지 않았고, Java의 `equals`를 사용하는 비교 부분에서 문제가 있었다. 송신 측 데이터 규격에 맞게 NULL·빈 문자열 비교 로직을 수정했다.

아래는 Oracle의 동작을 설명하는 학습 예시다. 당시 운영 SQL이나 수정 전후의 코드를 재현한 것은 아니다.

```sql
SELECT CASE WHEN '' IS NULL THEN 'NULL' ELSE 'VALUE' END AS empty_value
  FROM dual;
-- 결과: 'NULL' (NULL 값이 아니라 문자열)
```

빈 값의 저장·비교 원리는 [Oracle 빈 문자열과 NULL](/wiki/oracle-empty-string-is-null/)에 따로 정리했다. 일반적인 처리 방법과 이번에 실제 수행한 수정은 구분해서 읽어야 한다.

## 원인 2 — 송수신 처리 구분값의 규약 불일치

인터페이스에는 해당 데이터를 어떤 작업으로 처리할지 나타내는 구분값이 있었다. 송신 측이 보내는 값과 수신 프로시저가 처리 대상으로 인식하는 값이 맞지 않아 데이터가 정상 반영되지 않았다.

예를 들어 양쪽 모두 '수정' 작업을 뜻하더라도, 보내는 쪽의 코드와 받는 쪽이 분기 조건에 사용하는 코드가 다르면 의도한 처리가 실행되지 않는다. 이는 문제의 구조를 설명한 예시이며 실제 구분값은 적지 않는다.

상대 담당자와 송수신 데이터 형식을 협의해 맞추고, 인터페이스·프로시저의 반영 로직을 수정했다. 빈 값 비교만 고쳐서는 이 경로의 반영 누락이 해결되지 않으므로 별도로 다뤘다.

## 결과와 남긴 기준

NULL·빈 문자열 비교와 처리 구분값 반영을 각각 수정해, 이 오류로 월 34건 반복되던 불필요한 결재를 없앴다. 이는 해당 연계 오류로 발생하던 결재에 대한 결과이지 모든 결재나 모든 연계 오류가 사라졌다는 뜻은 아니다.

이 작업에서 오래 걸린 것은 복잡한 알고리즘을 만드는 일이 아니었다. 여러 계층에 흩어진 로직을 따라가며 같은 증상을 만드는 두 오류를 갈라내고, 상대 담당자와 규약을 맞추는 일이었다.

- 빈 값 비교와 수신값 반영을 별개의 확인 지점으로 본다.
- 인터페이스는 컬럼이 존재하는지만이 아니라 각 값의 의미와 수신 측 분기 조건까지 맞아야 한다.
- 같은 증상이 남아 있다고 해서 수정한 원인 하나만 다시 볼 것이 아니라, 다른 경로의 오류도 구분해서 확인한다.
