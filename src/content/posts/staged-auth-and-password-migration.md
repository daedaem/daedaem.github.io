> 코드와 테이블명은 문제의 구조를 보여주기 위해 일반적인 형태로 옮긴 것이다. 실제 시스템의 코드가 아니다.

대외 포털의 인증 구조를 다시 설계한 일이다. 두 가지를 바꿨다. 인증 절차를 단계로 나눈 것과, 비밀번호 저장 방식을 바꾼 것이다.

두 번째 항목에 대해 미리 적어 둘 것이 있다. 최종적으로 고른 방식은 계정별 salt를 적용한 범용 해시 함수다. 알고리즘은 운영 중인 시스템이라 적지 않는다. **지금 새로 설계한다면 이 선택은 하지 않는다.** 왜 그때 그것을 골랐고 무엇이 아쉬운지는 글 뒤에서 따로 쓴다.

## 1. 왜 단계를 나눠야 했는가

기존 구조는 로그인을 한 덩어리로 처리했다. ID와 비밀번호가 맞으면 인증된 사용자로 간주하고, 세션에 권한까지 실어 놓는 방식이다.

여기에 2차 인증을 추가해야 했다. 그런데 이 구조에 2차 인증을 끼워 넣으면 문제가 생긴다.

**1차 인증만 통과한 사용자가 이미 권한을 가진 상태가 된다.** 2차 인증 화면에 머물러 있는 동안 세션에는 권한이 실려 있다. 이 상태에서 다른 URL로 직접 요청을 보내면 어떻게 되는가. 화면 흐름으로만 2차 인증을 강제하고 있다면 통과된다.

비밀번호 변경 강제도 같은 문제를 갖고 있었다. 비밀번호를 바꿔야 하는 사용자를 변경 화면으로 보내지만, 그 사용자는 이미 로그인된 상태다.

즉 화면 이동으로 제어하던 것을 **상태로 제어**해야 했다.

## 2. 어떻게 나눴는가

인증을 세 단계로 분리하고, 각 단계를 통과해야만 다음 단계로 갈 수 있게 했다.

```
1단계  ID/비밀번호 검증
   ↓
2단계  2차 인증
   ↓
3단계  비밀번호 변경 필요 여부 판정
   ↓
인증 완료 — 이 시점에 비로소 권한을 적재한다
```

핵심은 **권한 적재를 최종 단계로 옮긴 것**이다.

중간 단계의 세션은 "이 사람이 누구인지 확인 중"인 상태이지 "이 사람은 이런 권한을 가졌다"는 상태가 아니다. 그러니 권한이 실려 있으면 안 된다. 중간 단계에서 다른 URL로 요청이 들어오면, 화면 흐름을 우회했든 아니든 권한이 없으므로 막힌다.

```java
public enum AuthStage {
    CREDENTIAL_VERIFIED,   // 1단계 통과. 아직 권한 없음
    SECOND_FACTOR_PASSED,  // 2단계 통과. 아직 권한 없음
    PASSWORD_CHECKED,      // 3단계 통과
    AUTHENTICATED          // 이 상태에서만 권한이 적재된다
}
```

각 단계 진입 시 이전 단계를 통과했는지 서버에서 확인한다. 클라이언트가 보내오는 값이 아니라 서버 세션의 상태로 판단한다.

이 확인은 URL 패턴별로 **요구 상태**를 매핑해 두고, 현재 상태가 미달이면 해당 단계로 되돌려 보내는 방식이다. 여기서 중요한 것은 기본값이다. 로그인·2차 인증·비밀번호 변경 화면처럼 낮은 상태로 열어 줄 URL만 명시하고, **그 외 전부는 인증 완료를 요구**하도록 두었다. 반대로 "막을 URL을 명시하는" 방식으로 짜면 화면을 하나 추가할 때마다 등록을 잊은 만큼 구멍이 생긴다. 등록을 잊었을 때 열리는 쪽이 아니라 막히는 쪽으로 실패해야 한다.

중간 단계의 세션에는 권한만이 아니라 사용자명도 넣지 않는다. 2차 인증을 통과하지 못한 상대에게 화면에 이름을 띄워 주는 것은 "이 아이디는 실재한다"를 확인해 주는 일이기 때문이다.

이렇게 바꾸고 나서 얻은 것은 보안뿐이 아니었다. 인증 절차에 단계를 추가하거나 순서를 바꾸는 일이 쉬워졌다. 단계가 명시적인 상태로 존재하니, 사이에 하나를 끼워 넣는 것이 흐름 전체를 헤집는 작업이 아니게 됐다.

### 단계를 나누는 것만으로는 부족하다

2차 인증을 붙이면 인증코드라는 새 자산이 생긴다. 여기에 따라오는 것들을 같이 정해야 한다. 적절한 값은 시스템마다 다르고 운영 중인 서비스의 값을 공개할 것도 아니므로, 무엇을 정해야 하는지만 적는다.

- **코드에 유효시간을 둔다.** 만료되지 않는 코드는 한 번 새면 계속 쓸 수 있다.
- **검증 실패 횟수를 제한하고, 넘으면 코드를 폐기한 뒤 재발급하게 한다.** 짧은 숫자 코드는 제한이 없으면 전수 대입으로 뚫린다. 여기서 중요한 것은 계정을 잠그는 것이 아니라 **코드를 폐기**하는 것이다. 잠그기만 하면 남의 계정을 잠그는 수단이 되어 버린다.
- **재발송에도 간격 제한을 둔다.** 없으면 발송 비용과 수신자 괴롭힘의 통로가 된다.
- **인증코드와 전화번호를 로그에 평문으로 남기지 않는다.** 인증을 아무리 잘 짜도 로그에 코드가 찍히면 로그 열람 권한이 곧 인증 우회 권한이 된다.

비밀번호 정책 검증도 같은 맥락이다. 화면에만 있던 검증은 **서버에도 둬야 한다.** 화면 검증은 사용자를 돕는 장치이지 막는 장치가 아니다. 요청을 직접 만들어 보내면 그대로 통과한다.

## 3. 비밀번호 저장 방식 바꾸기

기존 저장 방식은 그대로 둘 수 없는 상태였다. 구체적으로 어땠는지는 적지 않는다.

바꾼 방식은 **계정별 salt를 적용한 범용 해시 함수**다.

### salt가 왜 필요한가

salt 없이 해시만 저장하면 두 가지 문제가 있다.

**같은 비밀번호는 같은 해시가 된다.** 유출된 테이블을 보면 어떤 계정들이 같은 비밀번호를 쓰는지 드러난다. 한 계정이 뚫리면 나머지도 함께 뚫린다.

**레인보우 테이블이 통한다.** 흔한 비밀번호의 해시값을 미리 계산해 둔 표와 대조하면 원문이 바로 나온다.

계정마다 다른 salt를 붙여 해시하면 둘 다 막힌다. 같은 비밀번호라도 salt가 다르므로 해시가 달라지고, 미리 계산해 둔 표는 salt를 모르니 쓸모가 없다.

salt는 비밀이 아니다. 비밀번호와 함께 저장한다. 목적은 숨기는 것이 아니라 **미리 계산해 두지 못하게 하는 것**이다.

salt를 만들 때는 `Random`이 아니라 `SecureRandom`을 쓴다. `Random`은 시드를 알면 다음 값을 예측할 수 있다. 예측 가능한 salt는 미리 계산해 두지 못하게 한다는 목적을 그대로 무너뜨린다.

## 4. 서비스를 멈추지 않고 이행하기

여기가 실제로 까다로웠던 부분이다.

해시는 단방향이다. 저장된 값에서 원래 비밀번호를 되돌릴 수 없다. 그러니 **기존 사용자의 비밀번호를 일괄로 새 방식으로 다시 계산할 방법이 없다.** 원문을 모르기 때문이다.

선택지는 이랬다.

**전체 비밀번호 초기화.** 확실하지만 모든 사용자가 동시에 로그인하지 못하게 된다. 대외 포털에서 이건 사실상 서비스 중단이다.

**만료일을 두고 강제 변경.** 기한 내에 안 바꾼 계정은 잠긴다. 그래도 특정 시점에 다수가 몰린다.

**원문을 아는 시점에 순차 이행.** 사용자가 비밀번호를 평문으로 입력하는 순간이 원문을 알 수 있는 유일한 시점이다. 그때 새 방식으로 다시 저장한다.

세 번째를 골랐다. 원문을 아는 시점 중에서도 **비밀번호를 변경하는 시점**에 이행하도록 했다.

먼저 적어 둘 것이 있다. 이 방식의 표준은 **로그인 시점 재해시**다. 사용자가 로그인할 때 옛 방식으로 검증하고, 성공하면 그 순간 메모리에 있는 원문으로 새 방식의 해시를 만들어 저장한다. 사용자에게는 아무것도 요구하지 않고, Spring Security의 `DelegatingPasswordEncoder`가 지원하는 것도 이 흐름이다. 이번에 그 방식을 쓰지 못한 것은 기존 인증 흐름의 제약 때문이었다. 제약의 내용은 운영 중인 시스템의 구성이라 적지 않지만, 그 제약이 없었다면 로그인 시점이 맞다.

그래서 로그인 시점 대신 변경 시점을 고른 것인데, 이 선택이 가능했던 데는 이유가 있다. 앞에서 인증을 3단계로 나누면서 마지막 단계에 "비밀번호 변경 필요 여부 판정"을 두었다. 변경 대상으로 판정된 계정은 변경 페이지로 강제 전환된다. 즉 **이행을 밀어붙이는 장치가 이미 인증 흐름 안에 있었다.** 옛 형식으로 남아 있다는 것 자체를 변경 대상 조건에 넣으면, 사용자가 로그인하는 것만으로 변경 페이지를 거치게 되고 거기서 salt가 발급된다.

검증 로직은 두 형식을 모두 처리하도록 두었다. 아직 옮겨 가지 않은 계정도 로그인은 되어야 하기 때문이다.

```java
public boolean verify(Credential cred, String rawPassword) {
    // 저장된 값의 형식으로 옛 방식인지 새 방식인지를 구분한다
    if (cred.isLegacyFormat()) {
        return legacyHasher.matches(rawPassword, cred.getHash());
    }
    return hasher.matches(rawPassword, cred.getHash(), cred.getSalt());
}

// salt 발급은 원문을 다루는 유일한 지점, 즉 비밀번호 변경에서 일어난다
public void changePassword(String userId, String newRawPassword) {
    byte[] salt = new byte[16];
    new SecureRandom().nextBytes(salt);  // 계정마다 새로 생성한다. getInstanceStrong()은 Linux에서 블로킹될 수 있어 쓰지 않는다
    repository.updateCredential(userId, hash(newRawPassword, salt), salt);
}
```

이행 기간 동안 옛 형식 계정도 로그인이 막히지 않도록 두 형식을 함께 검증했고, 변경을 마친 계정은 새 형식으로 옮겨 갔다. 서비스는 멈추지 않았지만, 사용자에게 아무것도 요구하지 않은 것은 아니다. 엄밀히 말하면 "다음 로그인 때 비밀번호를 한 번 바꾸게 하는" 방식이고, 로그인 시점 재해시였다면 그마저 필요 없었을 것이다. 무중단이라는 말은 이 차이를 가리기 쉬워서 이 글에서는 쓰지 않는다.

이런 방식에는 관측 수단이 반드시 따라와야 한다. 옛 형식으로 남은 계정 수를 셀 수 있어야 이행이 어디까지 갔는지 알 수 있고, 장기 미접속 계정만 남는 시점에 별도 정책으로 처리할지 판단할 수 있다. 세지 못하면 순차 이행은 끝나는 시점을 알 수 없는 작업이 된다.

## 5. 지금이라면 다르게 고를 것

SHA-256 계열의 범용 해시는 **빠르게 설계된 해시**다. 파일 무결성 검증 같은 용도에서는 빠른 것이 장점이다.

비밀번호 저장에서는 이게 단점이 된다. 공격자가 유출된 해시를 두고 무차별 대입을 할 때, 해시가 빠를수록 초당 더 많이 시도할 수 있다. GPU를 쓰면 SHA-256은 초당 수십억 회 계산된다.

비밀번호용 해시는 **의도적으로 느리게** 설계되어 있다. bcrypt, scrypt, Argon2가 그렇다. 작업 계수를 조절해 한 번의 계산에 일부러 시간을 쓰게 만든다. 정상 로그인에서 0.1초는 문제가 안 되지만, 무차별 대입에서 0.1초는 시도 횟수를 수억 분의 일로 떨어뜨린다.

Spring Security를 쓴다면 `BCryptPasswordEncoder`가 기본 선택지고, `DelegatingPasswordEncoder`는 여러 인코더를 함께 두어 이 글에서 쓴 것과 같은 순차 이행을 표준적인 방식으로 지원한다.

```java
// 저장된 해시 앞에 {bcrypt}, {sha256} 같은 식별자가 붙어
// 계정마다 다른 방식으로 검증하면서 점진적으로 옮겨 갈 수 있다
PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
```

그때 범용 해시를 고른 이유는 기술적 판단만은 아니었다. 운영 환경의 제약과 도입 가능한 라이브러리의 범위, 그리고 합의 가능한 변경의 크기가 함께 작용했다. 지금 돌아보면 그 제약 안에서도 다른 선택이 가능했는지 더 따져 봤어야 했다고 생각한다.

다만 **아무것도 안 하는 것보다는 나았다.** 계정별 salt를 도입하는 것만으로도 레인보우 테이블과 해시 중복 노출은 막힌다. 완전한 해법이 당장 불가능할 때, 개선의 방향이 맞다면 부분적으로라도 옮겨 두는 편이 낫다는 것이 이 작업에서 얻은 판단이다.

## 정리

- 인증 절차에 단계를 추가할 때, 화면 흐름이 아니라 서버 상태로 강제해야 우회가 막힌다.
- 권한 적재는 모든 인증 단계를 통과한 뒤에 한다. 중간 단계의 세션에 권한이 있으면 그 자체가 구멍이다.
- salt는 비밀이 아니다. 계정마다 다르게 두어 미리 계산해 두지 못하게 하는 것이 목적이다.
- 해시는 되돌릴 수 없으므로 비밀번호 저장 방식은 일괄 이행이 불가능하다. 원문을 아는 시점, 즉 사용자가 입력하는 순간에 순차적으로 옮긴다. 표준은 로그인 시점 재해시이고, 변경 시점 이행은 그것이 불가능할 때의 차선이다.
- 인터셉터의 기본값은 최고 등급이어야 한다. 열어 줄 URL만 명시하고 나머지는 전부 막는다.
- 비밀번호 해시로는 범용 해시보다 bcrypt·scrypt·Argon2가 맞다. 빠른 것이 단점이 되는 드문 경우다.
- 순차 이행에는 관측 수단이 딸려 있어야 한다. 남은 수를 세지 못하면 언제 끝나는지 알 수 없다.
- 인증코드에는 유효시간·실패 횟수 제한·재발송 제한·로그 마스킹이 함께 와야 한다. 실패했을 때는 계정을 잠그는 것이 아니라 코드를 폐기한다.
- 제약 때문에 최선을 고를 수 없더라도, 방향이 맞는 개선은 부분적으로라도 해 두는 편이 낫다.
