> **정정(2026-09-14):** 기존 API 연동과 직접 개발한 업무 로직의 범위를 명확히 하고, 확인되지 않은 선택 과정과 구현 세부사항을 삭제했다. 회사·시스템명, 실제 연동 구성과 비용 수치는 공개하지 않는다.

업무 시스템에 Flash 기반 전자계약 모듈이 남아 있었다. 지원이 끝난 기술에 계약 기능이 의존하고 있었지만, 전체 고도화는 진행되지 못하고 있었다.

회의에서 이미 운영 중인 계약 시스템을 활용하는 방안이 제안됐고, 그 방안의 구현을 맡았다. 계약 기능 전체를 다시 만드는 대신 기존 계약 시스템의 API를 활용하고, 담당 시스템의 업무 흐름을 그 연동 방식에 맞게 바꾸는 작업이었다.

## API를 붙이는 것 외에 새로 만든 부분

기존 API가 있다고 해서 호출만 바꾸면 끝나는 일은 아니었다. 계약 요청 전후의 업무 처리와 상태 반영 로직이 옛 모듈에 맞춰져 있었다.

여러 계층에 흩어진 기존 연동 로직을 제거하고, 새 API 연동에 맞는 전후 업무 로직을 새로 개발했다. 이 글의 API는 기존 계약 시스템이 제공하던 연동 수단을 뜻한다. 상대 시스템의 API 자체를 새로 개발했다는 의미는 아니다.

수행 범위는 다음과 같다.

- 기존 계약 시스템 API에 맞춘 전자계약 연동과 요청 전후 처리 재구성
- 계약 진행 상태를 담당 시스템에 반영하는 동기화 배치
- 적재 실패 건을 초기 상태로 되돌리는 복구 처리
- 연동에서 제공되지 않는 세부 단계를 제외하는 상태 모델 정리

## 상태 동기화와 적재 실패 복구

전환 뒤에는 계약 시스템에도 데이터를 적재하는 흐름이 됐다. 계약 진행 상태는 배치가 주기적으로 담당 시스템에 반영하도록 구성했다.

적재에 실패한 건은 초기 상태로 되돌리도록 설계했다. 요청이 정상 처리되지 않았는데 진행 중인 것처럼 남으면 사용자가 다음 조치를 하기 어렵기 때문이다.

계약 작성 버튼은 기존 결재 상태에 연동되어 있었다. 상태가 초기 상태로 돌아가면 버튼이 다시 활성화되어 사용자가 재진입할 수 있었다. 별도의 실패 알림 화면을 새로 만든 것으로 설명하지 않는다.

이 흐름은 실패 건을 되돌리는 처리다. 사용자가 다시 요청할 수 있다는 것과 자동 재시도·중복 방지를 구현했다는 것은 다른 이야기이며, 후자의 구현 성과를 주장하지 않는다.

## 제공받지 못하는 상태는 남기지 않았다

기존 모듈에서 사용하던 세부 결재 단계 중에는 새로 연동한 API가 제공하지 않는 값이 있었다. 이 상태를 그대로 유지하면 실제 진행 상황과 맞지 않는 값이 화면에 남을 수 있었다.

계약 시스템이 제공하는 범위에 맞춰 상태 모델을 줄였다. API가 주지 않는 단계를 임의로 추정해서 채우지 않고, 연동에서 확인할 수 있는 상태만 반영하도록 했다.

## 결과

기존 계약 시스템 API 연동과 전후 업무 로직 개발로 Flash 기반 전자계약 모듈을 대체하고, 기존 환경의 유지보수 계약을 해지할 수 있게 됐다. 비용 수치는 이 글에 공개하지 않는다.

재사용한 것은 상대 시스템의 계약 기능과 API다. 새로 개발한 것은 그것을 담당 시스템의 업무에 연결하는 전후 처리, 상태 동기화와 실패 복구 흐름이다. 두 범위를 구분하는 것이 이 작업을 설명하는 핵심이다.
