> 어느 시스템과 어느 외부 서버인지는 적지 않는다. 에러 메시지와 버전별 동작은 일반적인 사실이다.

구버전 JDK로 돌아가는 시스템에서 외부 서버에 HTTPS로 붙으려다 핸드셰이크 단계에서 막혔다. 코드를 아무리 들여다봐도 연결 자체가 안 되는 상황이었다.

## 에러가 원인을 안 알려준다

이런 종류의 메시지가 나온다.

```
Could not generate DH keypair
Received fatal alert: handshake_failure
The server selected protocol version TLS10 is not accepted
```

메시지만 보면 암호 로직 문제 같지만, 실제로는 대부분 **클라이언트의 JDK가 서버가 요구하는 수준을 따라가지 못해서** 생긴다.

## 버전별로 갈리는 지점

| | 기본 TLS | DH 키 길이 |
|---|---|---|
| JDK 6 | TLS 1.0 | 1024비트 초과 처리 불가 |
| JDK 7 | TLS 1.0 (1.2는 옵션으로 활성화) | 2048비트 지원 |
| JDK 8 이상 | TLS 1.2 | 제약 없음 |

요즘 서버는 보통 **TLS 1.2 이상만 허용**하고 **2048비트 DH 파라미터**를 내려준다. 그러면 구버전 클라이언트는 두 가지 모두에서 걸린다. 코드를 고쳐서 될 문제가 아니고 **런타임 자체의 한계**다.

서버 설정을 낮춰 달라고 요청할 수도 있지만, 보안 때문에 올린 것을 다시 낮추는 것은 반대 방향이다. 요청하지 않았다.

## 선택지

1. **JDK 업그레이드.** 정답이다. 다만 운영 시스템은 WAS·프레임워크·라이브러리가 묶여 있어 런타임 하나만 올리기가 어렵다.
2. **별도 모듈 분리.** 통신 부분만 상위 버전 런타임으로 띄우고 기존 시스템과 연결한다. 관리할 것이 하나 늘어난다.
3. **이미 연결된 경로 경유.** 목적지에 닿는 다른 경로가 사내에 이미 있다면 그것을 탄다. 새로 만드는 게 아니라 있는 것을 쓰는 것이라 리스크가 작다.

## 판단 기준

레거시에서는 "제대로 된 방법"과 "지금 할 수 있는 방법"이 갈라진다. 이 순서로 본다.

- 이 기능 하나 때문에 **시스템 전체의 런타임을 올리는 것이 맞는가.**
- 올린다면 회귀 범위는 어디까지인가. 같은 런타임을 쓰는 기능이 몇 개인가.
- 대안 경로가 있다면 그것은 **임시방편인가, 구조적으로 안정적인가.**

런타임을 못 올리는 상황에서 우회를 고르는 것은 타협이다. 다만 **그 선택을 기록으로 남겨 두면** 나중에 업그레이드할 때 어디를 걷어내면 되는지가 분명해진다.

## 정리

- TLS 핸드셰이크 실패 메시지는 암호 로직이 아니라 런타임 버전을 먼저 의심한다.
- JDK 6·7은 기본 TLS 1.0이고 DH 키 길이 제약이 있다. TLS 1.2와 2048비트를 요구하는 서버에는 붙지 못한다.
- 서버 보안 수준을 낮추는 요청은 하지 않는다.
- 런타임을 올릴 수 없다면 통신 모듈 분리나 기존 경로 경유가 선택지이고, 어느 쪽이든 왜 그렇게 했는지를 남긴다.
