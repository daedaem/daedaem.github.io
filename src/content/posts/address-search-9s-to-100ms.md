> 테이블명·컬럼명·인덱스명은 일반적인 이름으로 바꿨고, 실행 계획의 비용 값은 형태만 보여주는 예시다. 응답 시간과 데이터 규모는 당시 기록한 값이다.

사내 시스템에서 주소를 검색하면 최대 9초가 걸렸다. 사용자는 주소 한 건을 넣기 위해 화면 앞에서 기다렸고, 검색을 두세 번 고쳐 하는 일이 잦으니 체감은 그보다 나빴다.

느린 것만이 문제가 아니었다. 들여다보게 된 계기는 장애였다. WAS 로그에서 메모리 부족(OOM)과 이어진 WAS 다운을 확인했다. 메모리 분석 도구도 사용했지만, 그 결과만으로 특정 조회가 원인이라고 확정한 것은 아니었다. 로그와 조건 없는 전체 조회 경로를 근거로 이 조회를 먼저 의심했고, 검색 조건을 필수로 바꿔 전체 조회 경로를 막았다.

조건 없는 전체 조회를 막고 쿼리를 고쳤고(9초 → 1초대), DB에 없는 주소를 그때마다 추가해야 하는 작업이 남아 조회 대상 자체를 외부 서비스로 바꿨다(외부 API 응답 100밀리초대). 대신 외부 의존이 생겼고, 그건 아직 남아 있는 위험이다.

수치는 측정 대상을 나눠 적는다. 9초에서 1초대까지는 자체 DB 조회의 개선이고, 100밀리초대는 팝업으로 전환한 뒤 브라우저 네트워크에서 확인한 검색 요청 응답 시간이다. 외부 검색을 선택하고 기존 화면에 연동해 수기 적재를 없앤 것도 이 작업의 성과다.

조회 속도를 개선한 뒤에도 반복되던 주소 추가 작업을 어떻게 없앴는지가 이 글의 본론이다.

## 1. 느린 이유를 확인하다

주소 테이블은 약 600만 건이었다. 시·군·동·건물·도로명은 각각 별도 컬럼에 저장되어 있었다. 첫 번째로 개선한 쿼리는 전체 주소 문자열이 아니라 **도로명 컬럼을 검색하는 쿼리**였다. 도로명 검색어의 앞뒤에 와일드카드를 붙여 조회하고 있었다.

아래의 `road_name`은 실제 컬럼명을 일반화한 이름이다. 검색 조건을 중심으로 쿼리를 줄이면 다음과 같다.

```sql
SELECT road_name, zip_code
  FROM address_master
 WHERE road_name LIKE '%' || #{keyword} || '%'
```

`road_name`에는 인덱스가 있었다. 그런데도 느렸다. 실행 계획을 뜨자 이유가 바로 보였다.

> 아래 실행 계획은 **형태를 보여주기 위한 예시**다. 실제 출력의 비용 값과 객체명은 그대로 옮기지 않았다. 확인한 사실은 `TABLE ACCESS FULL`이 찍혔다는 것이다.

```
--------------------------------------------------------------
| Id | Operation         | Name           | Rows  | Cost      |
--------------------------------------------------------------
|  0 | SELECT STATEMENT  |                |       |     8871  |
|* 1 |  TABLE ACCESS FULL| ADDRESS_MASTER |  6013K|     8871  |
--------------------------------------------------------------
```

`INDEX RANGE SCAN`이 아니라 `TABLE ACCESS FULL`이었다. 인덱스가 있는데도 쓰지 않았다.

### 선행 와일드카드는 범위 스캔을 어렵게 한다

B-tree 인덱스는 값을 정렬해 두고, 앞에서부터 비교해 범위를 좁히는 자료구조다. 전화번호부에서 "김"으로 시작하는 이름을 찾을 때 첫 글자로 위치를 특정할 수 있는 것과 같다.

`LIKE '테헤란%'`은 이 성질을 쓸 수 있다. 시작 문자열이 고정되어 있으니 정렬된 인덱스에서 `테헤란`으로 시작하는 구간만 읽으면 된다.

`LIKE '%테헤란%'`은 일반적인 B-tree 인덱스로 검색 시작 범위를 좁힐 수 없다. 어디에서 시작하는지 알 수 없기 때문이다. 전화번호부에서 이름 중간에 특정 글자가 들어간 사람을 찾으라는 요구와 같다. 옵티마이저가 인덱스 전체를 훑는 방식을 고를 수는 있지만, `INDEX RANGE SCAN`으로 필요한 구간만 읽는 이점은 얻지 못한다. 이번 실행 계획에서는 테이블 전체 스캔이 선택됐다.

앞에 붙은 `%` 때문에 검색 시작 범위를 좁히는 이점을 얻지 못한 것이다. 이걸 선행 와일드카드(leading wildcard)라고 부른다.

### 전방 일치로 바꾸다

```sql
SELECT road_name, zip_code
  FROM address_master
 WHERE road_name LIKE #{keyword} || '%'
```

조건을 바꾸고 다시 실행 계획을 떴다. (아래도 예시 형태다)

```
--------------------------------------------------------------
| Id | Operation                   | Name          | Cost     |
--------------------------------------------------------------
|  0 | SELECT STATEMENT            |               |       42 |
|  1 |  TABLE ACCESS BY INDEX ROWID| ADDRESS_MASTER|       42 |
|* 2 |   INDEX RANGE SCAN          | IX_ADDR_ROAD  |        4 |
--------------------------------------------------------------
```

`INDEX RANGE SCAN`으로 바뀌었고 9초가 1초대로 줄었다.

### 조건 없는 조회를 막다

쿼리를 고치는 것과 별개로, 검색어가 비어 있으면 조회 자체를 거부하도록 조건을 필수로 만들었다. 인덱스 사용 여부와 별개로 전체 결과를 WAS 메모리에 올리는 경로는 남겨 둘 수 없었다.

검색어를 필수로 받는 것과 결과 수를 제한하는 것은 별개다. 짧은 전방 일치 검색어도 많은 행을 반환할 수 있으므로, 같은 방식을 다시 설계한다면 결과 상한·페이징과 넓은 검색 조건에서의 메모리 사용량도 검증해야 한다.

### 검색 대상과 개선 범위

전방 일치로 바꾼 것은 별도 컬럼에 저장된 도로명 검색이다. 시·군·동·건물 정보를 합친 전체 주소의 중간 단어 검색은 손대지 않았다.

## 2. 쿼리를 고쳐도 남는 문제

조회가 빨라진 뒤에도 필요한 주소가 DB에 없는 경우가 있었다. 그때마다 주소 데이터를 추가해야 했다. **없는 주소를 건건이 추가하는 반복 작업**이 외부 API로 전환한 큰 이유였다.

쿼리를 개선하면 이미 저장된 주소는 빨리 찾을 수 있다. 하지만 DB에 없는 주소까지 검색할 수 있게 되는 것은 아니다. 조회 성능을 개선하는 것과 주소를 계속 추가해야 하는 일을 줄이는 것은 별개의 문제였다.

## 3. 조회 방식을 바꾸다

행정안전부가 도로명주소 검색 팝업을 여는 API를 공개하고 있었다. 우리 화면에서 주소를 입력하던 자리에 이 팝업을 띄우고, 사용자가 고른 주소를 콜백으로 받는 방식으로 바꿨다.

검색 입력부터 결과 목록, 선택까지의 화면을 상대가 제공하므로 우리 쪽은 결과를 받는 콜백 하나만 만들면 됐다. 붙이는 비용이 가장 낮은 방식이었다. 대신 브라우저가 다른 도메인의 창을 여는 구조라는 점이 뒤에 적을 폴백 설계에 영향을 준다.

- 응답 시간은 브라우저 네트워크 탭 기준 100밀리초대가 됐다. 우리 DB를 뒤지지 않고 상대 서비스의 응답을 받는 것이니, 이 수치는 우리가 튜닝해서 얻은 것이 아니다.
- 자체 DB에 없는 주소를 검색할 때마다 데이터를 추가하던 작업을 없앴다. 주소 조회와 데이터 갱신을 외부 서비스에 맡겼다.

API로 전환한 큰 이유는 **주소가 없을 때마다 데이터를 추가해야 하는 반복 작업을 없애는 것**이었다. 쿼리 튜닝은 조회 속도를 개선했고, 외부 API 연동은 이 운영 작업을 줄이기 위한 선택이었다.

## 4. 남은 위험 — 외부 의존

여기서 새 위험이 생긴다. 우리 통제 밖의 시스템에 기능이 매달린다. 팝업이 열리지 않거나 상대 서비스가 멎으면 주소 검색이 멎는다. 이 위험은 아직 해소하지 않았다. 아래는 대체 경로를 검토하면서 정리한 내용이고, 구현한 것은 아니다.

후보는 인덱스를 타도록 고친 기존 DB 조회를 **대체 경로로 남기는 것**이다. 팝업이 안 될 때 사용자가 넘어갈 수 있는 두 번째 검색이다.

### 팝업 내부의 실패를 직접 감지하기 어려운 이유

서버가 API를 호출하는 구조라면 호출 실패를 잡아 대체 조회로 넘기는 경로를 만들 수 있다. 아래는 그 분기만 보여 주는 예시다. 실제 설계에는 타임아웃, 대체 조회의 부하와 데이터 최신성, 전환 여부를 확인할 수 있는 로그가 함께 필요하다.

```java
// 서버 호출 구조였다면 이렇게 됐을 것이다. 이번 구조에서는 쓰지 않았다.
try {
    return addressApiClient.search(keyword);   // 연결·읽기 타임아웃 짧게
} catch (ApiUnavailableException e) {
    log.warn("주소 API 실패, 내부 조회로 대체", e);  // 폴백 발생을 관측 대상으로
    return addressMapper.searchByPrefix(keyword);
}
```

다른 도메인의 팝업은 내부 문서를 직접 읽을 수 없다(same-origin policy). 창을 열었더라도 그 안이 오류 페이지인지 정상 검색 화면인지 우리 페이지에서 직접 판별하기 어렵다. 상대 팝업이 `postMessage` 같은 방식으로 결과를 알려주는 협력 규약이 있다면 별도 설계가 가능하지만, 이 작업에서는 그런 실패 감지와 자동 전환을 구현하지 않았다.

감지가 불확실한 자동 전환은 두 가지로 잘못될 수 있다. 실패를 못 알아채 사용자가 빈 창 앞에 남거나, 정상인데 실패로 오판해 낡은 내부 데이터를 준다. 그래서 둔다면 **사용자가 고를 수 있는 명시적인 대체 경로**여야 한다. 주소 검색 버튼 옆에 "검색이 안 될 때" 성격의 버튼을 두고 내부 조회로 연결하는 형태다.

대체 조회도 데이터가 낡으면 잘못된 주소를 줄 수 있다. 실제 도입하려면 갱신 기준, 마지막 갱신 시점 안내, 검색되지 않을 때의 처리 절차까지 정해야 한다. 외부 의존을 없애는 것이 아니라 별도의 유지 비용과 맞바꾸는 선택이다.

## 정리

- 선행 와일드카드 `LIKE '%x%'`는 B-tree 인덱스로 검색 시작 범위를 좁힐 수 없다. 실행 계획의 `TABLE ACCESS FULL`로 확인했다.
- 9초 → 1초대는 DB 개선이고, 100밀리초대는 외부 API 응답이다. 둘을 한 수치로 붙이지 않는다.
- 도로명은 다른 주소 항목과 별도 컬럼에 저장되어 있었다. 도로명 검색 쿼리를 개선한 뒤에도 없는 주소를 추가하는 작업은 남았다. 이 반복 작업을 없애기 위해 외부 API로 조회 방식을 바꿨다.
- 외부 서비스로 옮기면 갱신 책임은 넘어가지만 가용성에 의존하게 된다. 팝업 내부 실패를 직접 감지하기 어려웠고, 자동 전환과 수동 대체 경로는 아직 만들지 않았다.

쿼리를 개선해 조회 시간을 줄이는 데서 끝내지 않고, 없는 주소를 그때마다 추가해야 했던 작업까지 없앴다. 이 사례에서 성능 개선과 API 전환을 나누어 설명하는 이유다.

**정정(2026-10-02):** 검색 대상이 전체 주소가 아니라 별도 도로명 컬럼이었다는 점을 바로잡았다. 전체 주소의 중간 단어 검색을 잃었다는 설명과, 그 손실을 전제로 실제 검토한 것처럼 적었던 대안 비교를 삭제했다.

**보완(2026-10-02):** 외부 API 전환의 큰 이유가 없는 주소를 그때마다 추가해야 하는 반복 작업이었다는 점을 명확히 했다.
