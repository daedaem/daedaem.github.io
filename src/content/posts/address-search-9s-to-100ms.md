> 테이블명·컬럼명·인덱스명은 일반적인 이름으로 바꿨고, 실행 계획의 비용 값은 형태만 보여주는 예시다. 응답 시간과 데이터 규모는 당시 기록한 값이다. 브라우저 네트워크 탭의 요청 소요 시간은 화면 렌더링 완료까지의 시간과 다르다. DB 조회 요청과 외부 API 요청 역시 측정 대상이 달라 직접적인 개선 배수로 비교하지 않는다.

사내 시스템에서 주소를 검색하면 최대 9초가 걸렸다. 사용자는 주소 한 건을 넣기 위해 화면 앞에서 기다렸고, 검색을 두세 번 고쳐 하는 일이 잦으니 체감은 그보다 나빴다.

느린 것만이 문제가 아니었다. 이 문제를 들여다보게 된 계기 자체가 장애였다. WAS 로그에 메모리 부족(OOM)이 남아 있었고, 그 직전에 이 주소 조회가 검색어 없이 두 번 연속 실행된 기록이 있었다. 검색어가 비면 전체 데이터를 가져오려 하는 경로가 있었고, 그것이 연달아 돌면서 힙을 채운 것이다.

순서는 장애 로그, 다운 직전의 쿼리, 그 쿼리의 실행 계획이었다. 로그가 어느 조회가 연달아 돌다 메모리가 바닥났는지를 보여 줬고, 실행 계획은 그 조회가 왜 그렇게 비쌌는지를 설명했다. 전체 조회 경로부터 막기로 했다.

조건 없는 전체 조회를 막고 쿼리를 고쳤고(9초 → 1초대), 그래도 남는 운영 문제 때문에 조회 대상 자체를 외부 서비스로 바꿨다(외부 API 응답 100밀리초대). 대신 외부 의존이 생겼고, 그건 아직 남아 있는 위험이다.

숫자 하나는 미리 갈라 두어야 한다. 9초에서 1초대까지가 DB 쪽 개선이고, 100밀리초대는 DB 튜닝의 성과가 아니라 외부 API의 응답 시간이다. 이 둘을 한 줄로 붙여 "9초를 100밀리초로 줄였다"고 말하면 절반은 남의 성과를 가져오는 셈이 된다.

쿼리를 고쳐 목표 수치를 만족했는데도 왜 거기서 멈추지 않았는지가 이 글의 본론이다.

## 1. 느린 이유를 확인하다

주소 테이블은 약 600만 건이었다. 조회 쿼리는 대략 이런 모양이었다.

```sql
SELECT road_addr, jibun_addr, zip_code
  FROM address_master
 WHERE road_addr LIKE '%' || #{keyword} || '%'
```

`road_addr`에는 인덱스가 있었다. 그런데도 느렸다. 실행 계획을 뜨자 이유가 바로 보였다.

> 아래 실행 계획은 **형태를 보여주기 위한 예시**다. 실제 출력의 비용 값과 객체명은 그대로 옮기지 않았다. 확인한 사실은 `TABLE ACCESS FULL`이 찍혔다는 것이다.

```
--------------------------------------------------------------
| Id | Operation         | Name           | Rows  | Cost      |
--------------------------------------------------------------
|  0 | SELECT STATEMENT  |                |       |     8871  |
|* 1 |  TABLE ACCESS FULL| ADDRESS_MASTER |  6013K|     8871  |
--------------------------------------------------------------
```

`INDEX RANGE SCAN`이 아니라 `TABLE ACCESS FULL`이었다. 인덱스가 있는데도 쓰지 않았다.

### 선행 와일드카드가 인덱스를 무력화한다

B-tree 인덱스는 값을 정렬해 두고, 앞에서부터 비교해 범위를 좁히는 자료구조다. 전화번호부에서 "김"으로 시작하는 이름을 찾을 때 첫 글자로 위치를 특정할 수 있는 것과 같다.

`LIKE '서울%'`은 이 성질을 쓸 수 있다. 시작 문자열이 고정되어 있으니 정렬된 인덱스에서 `서울`로 시작하는 구간만 읽으면 된다.

`LIKE '%서울%'`은 일반적인 B-tree 인덱스로 검색 시작 범위를 좁힐 수 없다. 어디에서 시작하는지 알 수 없기 때문이다. 전화번호부에서 "이름 중간에 '서울'이 들어간 사람"을 찾으라는 요구와 같다. 옵티마이저가 인덱스 전체를 훑는 방식을 고를 수는 있지만, `INDEX RANGE SCAN`으로 필요한 구간만 읽는 이점은 얻지 못한다. 이번 실행 계획에서는 테이블 전체 스캔이 선택됐다.

앞에 붙은 `%` 때문에 검색 시작 범위를 좁히는 이점을 얻지 못한 것이다. 이걸 선행 와일드카드(leading wildcard)라고 부른다.

### 전방 일치로 바꾸다

```sql
SELECT road_addr, jibun_addr, zip_code
  FROM address_master
 WHERE road_addr LIKE #{keyword} || '%'
```

조건을 바꾸고 다시 실행 계획을 떴다. (아래도 예시 형태다)

```
--------------------------------------------------------------
| Id | Operation                   | Name          | Cost     |
--------------------------------------------------------------
|  0 | SELECT STATEMENT            |               |       42 |
|  1 |  TABLE ACCESS BY INDEX ROWID| ADDRESS_MASTER|       42 |
|* 2 |   INDEX RANGE SCAN          | IX_ADDR_ROAD  |        4 |
--------------------------------------------------------------
```

`INDEX RANGE SCAN`으로 바뀌었고 9초가 1초대로 줄었다.

### 조건 없는 조회를 막다

쿼리를 고치는 것과 별개로, 검색어가 비어 있으면 조회 자체를 거부하도록 조건을 필수로 만들었다. 인덱스 사용 여부와 별개로 전체 결과를 WAS 메모리에 올리는 경로는 남겨 둘 수 없었다. 이후 같은 증상의 다운은 없었다.

### 대신 잃은 것

전방 일치는 검색 결과의 성격을 바꾼다. 예를 들어 `서울특별시 강남구 테헤란로`는 `%강남%`에 일치하지만 `강남%`에는 일치하지 않는다. 사용자가 주소 중간의 단어로 검색하던 사용 방식이 막힌다.

이건 성능과 기능을 맞바꾼 것이지 공짜로 얻은 개선이 아니다. 이 지점에서 판단이 갈렸다.

## 2. 고르지 않은 선택지들

전방 일치의 검색 범위 손실을 메우는 방법은 여럿 있었다.

**Oracle Text (CONTEXT 인덱스)**
전문 검색 인덱스를 만들면 `CONTAINS`로 중간 일치를 인덱스로 처리할 수 있다. 정공법이다. 다만 인덱스 동기화 주기를 관리해야 하고, 운영 DB에 새 인덱스 유형을 도입하려면 DBA 협의와 검증이 필요했다. 무엇보다 아래에 적을 근본 문제를 해결하지 못한다.

**역방향 컬럼 추가**
`REVERSE(road_addr)`를 컬럼으로 두고 인덱스를 걸면 후방 일치(`%강남`)까지는 커버된다. 중간 일치는 여전히 안 된다. 컬럼과 인덱스가 늘고 적재 로직이 복잡해지는 데 비해 얻는 게 적었다.

**검색 엔진 도입**
Elasticsearch 같은 것을 붙이면 깔끔하지만, 운영 중인 환경에 새 미들웨어를 세우는 일은 이 문제의 규모에 비해 과했다. 판단이라기보다 현실적 제약이었다.

이 선택지들을 검토하다가, 셋 다 같은 것을 전제하고 있다는 걸 깨달았다. **주소 데이터를 우리가 계속 들고 있는다는 전제다.**

## 3. 쿼리를 고쳐도 남는 문제

주소 테이블 600만 건은 어디서 왔는가. 우체국이 배포하는 주소 데이터 파일을 누군가 주기적으로 받아 수기로 적재하고 있었다.

주소는 계속 바뀐다. 도로명이 신설되고, 건물이 생기고, 행정구역이 조정된다. 그때마다 최신 데이터를 받아 넣어야 하는데, 이건 사람이 기억해서 하는 일이었다. 적재가 밀리면 최근에 생긴 주소가 검색되지 않는다. 사용자 입장에서는 "검색이 안 되는" 버그다.

쿼리를 아무리 잘 고쳐도 이 문제는 그대로 남는다. 조회가 빨라진다고 낡은 주소가 최신 주소가 되지는 않는다.

## 4. 조회 방식을 바꾸다

행정안전부가 도로명주소 검색 팝업을 여는 API를 공개하고 있었다. 우리 화면에서 주소를 입력하던 자리에 이 팝업을 띄우고, 사용자가 고른 주소를 콜백으로 받는 방식으로 바꿨다.

검색 입력부터 결과 목록, 선택까지의 화면을 상대가 제공하므로 우리 쪽은 결과를 받는 콜백 하나만 만들면 됐다. 붙이는 비용이 가장 낮은 방식이었다. 대신 브라우저가 다른 도메인의 창을 여는 구조라는 점이 뒤에 적을 폴백 설계에 영향을 준다.

- 응답 시간은 브라우저 네트워크 탭 기준 100밀리초대가 됐다. 우리 DB를 뒤지지 않고 상대 서비스의 응답을 받는 것이니, 이 수치는 우리가 튜닝해서 얻은 것이 아니다.
- 데이터 최신성 문제가 사라졌다. 갱신은 원본을 관리하는 쪽의 책임이 됐다.
- 수기 적재 운영이 없어졌다. 사람이 기억해서 해야 하는 일이 하나 줄었다.
- 검색 범위 손실도 함께 해결됐다. API는 중간 일치 검색을 지원한다.

성능 개선은 사실 부수 효과에 가까웠다. 없애고 싶었던 것은 **우리가 관리할 이유가 없는 데이터를 관리하고 있었다는 사실**이었다.

## 5. 남은 위험 — 외부 의존

여기서 새 위험이 생긴다. 우리 통제 밖의 시스템에 기능이 매달린다. 팝업이 열리지 않거나 상대 서비스가 멎으면 주소 검색이 멎는다. 이 위험은 아직 해소하지 않았다. 아래는 대체 경로를 검토하면서 정리한 내용이고, 구현한 것은 아니다.

후보는 인덱스를 타도록 고친 기존 DB 조회를 **대체 경로로 남기는 것**이다. 팝업이 안 될 때 사용자가 넘어갈 수 있는 두 번째 검색이다.

### 자동 전환이 성립하지 않는 이유

서버가 API를 호출하는 구조였다면 폴백은 코드 몇 줄이다. 예외를 잡아 내부 조회로 내려가고, 타임아웃을 걸고, 내려갔다는 로그를 남기면 된다.

```java
// 서버 호출 구조였다면 이렇게 됐을 것이다. 이번 구조에서는 쓰지 않았다.
try {
    return addressApiClient.search(keyword);   // 연결·읽기 타임아웃 짧게
} catch (ApiUnavailableException e) {
    log.warn("주소 API 실패, 내부 조회로 대체", e);  // 폴백 발생을 관측 대상으로
    return addressMapper.searchByPrefix(keyword);
}
```

그런데 브라우저가 다른 도메인의 팝업을 여는 구조에서는 이게 성립하지 않는다. 팝업 창 안에서 무슨 일이 났는지 우리 페이지는 알 수 없다. 다른 출처의 창은 읽을 수 없기 때문이다(same-origin policy). 창이 떴는지까지는 알아도, 그 안이 오류 페이지인지 정상 검색 화면인지는 구분되지 않는다.

감지가 불확실한 자동 전환은 두 가지로 잘못될 수 있다. 실패를 못 알아채 사용자가 빈 창 앞에 남거나, 정상인데 실패로 오판해 낡은 내부 데이터를 준다. 그래서 두게 된다면 **사용자가 고를 수 있는 명시적인 대체 경로**여야 한다. 주소 검색 버튼 옆에 "검색이 안 될 때" 성격의 버튼을 두고 내부 조회로 연결하는 형태다.

대체 조회도 데이터가 낡으면 잘못된 주소를 줄 수 있다. 실제 도입하려면 갱신 기준, 마지막 갱신 시점 안내, 검색되지 않을 때의 처리 절차까지 정해야 한다. 외부 의존을 없애는 것이 아니라 별도의 유지 비용과 맞바꾸는 선택이다.

## 정리

- 선행 와일드카드 `LIKE '%x%'`는 B-tree 인덱스로 검색 시작 범위를 좁힐 수 없다. 실행 계획의 `TABLE ACCESS FULL`로 확인했다.
- 9초 → 1초대는 DB 개선이고, 100밀리초대는 외부 API 응답이다. 둘을 한 수치로 붙이지 않는다.
- 전방 일치 전환은 성능을 얻고 검색 범위를 잃는 거래였다. 수치는 만족했지만 데이터가 낡는 문제는 그대로였고, 그래서 조회 대상 자체를 바꿨다.
- 외부 서비스로 옮기면 갱신 책임은 넘어가지만 가용성에 의존하게 된다. 팝업 구조에서는 실패 감지가 불확실해 자동 전환이 성립하지 않고, 수동 대체 경로는 아직 만들지 않았다.

수치를 만족했을 때 멈추지 않은 것이 이 작업에서 가장 잘한 판단이었다고 생각한다. 9초를 1초로 줄인 것보다, 애초에 우리가 들고 있을 이유가 없던 데이터를 내려놓은 쪽이 오래 가는 개선이었다.
