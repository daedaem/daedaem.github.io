> 코드와 테이블명은 문제의 구조를 보여주기 위해 일반적인 형태로 옮긴 것이다. 실제 시스템의 코드가 아니다.

WEB/WAS 전환 작업 중 **개발 서버**에서 있었던 일이다. 새 컨테이너로 애플리케이션을 올리고, 확인을 마친 뒤 기존 컨테이너를 내렸다.

그런데 배치가 계속 돌았다. 내린 쪽에서 돌 리가 없고, 새로 올린 쪽에는 아직 해당 배치를 걸지 않은 상태였다. 그런데 데이터는 주기적으로 갱신되고 있었다.

## 상황 정리

확실한 것부터 정리했다.

- 데이터가 실제로 바뀌고 있다. 이건 조회로 확인된다.
- 갱신 주기가 배치 주기와 일치한다. 사람이 손으로 하는 게 아니다.
- 기존 컨테이너는 종료 명령을 내렸고, 내려간 것으로 알고 있었다.
- 새 컨테이너에는 이 배치가 등록되어 있지 않다.

즉 **우리가 알고 있는 한, 두 곳 어디도 아닌 무언가가 DB를 갱신하고 있었다.** 이 "알고 있는 한"이 나중에 문제의 핵심으로 드러난다.

개발 서버라 당장의 피해는 없었다. 그래도 그냥 둘 수 없었던 이유가 둘 있다. 어디서 도는지 모르는 프로세스가 데이터를 만지는 동안은 전환 검증 결과를 믿을 수 없다는 것, 그리고 같은 절차로 운영을 전환했을 때 같은 일이 벌어지면 새 컨테이너에 배치를 거는 순간 **두 곳에서 중복 실행**된다는 것이다. 운영에서 겪기 전에 개발에서 원인을 알아 두어야 했다.

## 왜 로그로 못 찾았는가

가장 먼저 할 일은 애플리케이션 로그를 보는 것이다. 하지만 로그를 볼 수 있으려면 어느 서버의 로그를 봐야 하는지를 알아야 한다. 우리가 모르는 것이 바로 그것이었다. 의심되는 주체가 그 애플리케이션 밖에 있다면, 그 애플리케이션 로그에는 아무것도 찍히지 않는다.

처음에는 새 서버 안을 뒤졌다. 스케줄러 설정이 어디에 남아 있는지, 어떤 경로로 배치가 살아 있을 수 있는지. 아무것도 나오지 않았다.

돌이켜보면 이 시점에 DB 세션부터 봤어야 했다. Oracle이라면 이런 조회가 가능하다.

```sql
SELECT sid, serial#, machine, osuser, program, logon_time
  FROM v$session
 WHERE program IS NOT NULL
 ORDER BY logon_time DESC;
```

`v$session`의 `machine`이나 `program`으로 접속 출처를 볼 수 있다. WAS는 보통 커넥션 풀로 세션을 계속 붙여 두므로, 잔존 프로세스가 있었다면 여기에 잡혔을 가능성이 크다. 다만 이 뷰는 지금 연결된 세션만 보여 주고, 풀 없이 짧게 붙었다 끊는 배치라면 잡기 어렵다. 그때는 이쪽을 보지 않았고, 아래 방법으로 갔다. 지금 다시 한다면 `v$session`을 먼저 보고, 거기서 안 나올 때 트리거를 걸 것이다.

그래서 택한 방향은 이것이었다. **세션을 실시간으로 잡는 대신, 갱신이 일어날 때 스스로 흔적을 남기게 하자.**

## 트리거로 흔적을 남기다

갱신되는 테이블에 UPDATE 트리거를 걸고, 그 시점의 접속 정보를 별도 로그 테이블에 쌓았다.

```sql
CREATE TABLE update_trace_log (
    logged_at   DATE,
    db_user     VARCHAR2(100),
    os_user     VARCHAR2(100),
    host_name   VARCHAR2(100),
    client_ip   VARCHAR2(100),
    module      VARCHAR2(100)
);
```

```sql
CREATE OR REPLACE TRIGGER trg_trace_update
AFTER UPDATE ON target_table
FOR EACH ROW
BEGIN
    INSERT INTO update_trace_log (
        logged_at, db_user, os_user, host_name, client_ip, module
    ) VALUES (
        SYSDATE,
        SYS_CONTEXT('USERENV', 'SESSION_USER'),
        SYS_CONTEXT('USERENV', 'OS_USER'),
        SYS_CONTEXT('USERENV', 'HOST'),
        SYS_CONTEXT('USERENV', 'IP_ADDRESS'),
        SYS_CONTEXT('USERENV', 'MODULE')
    );
EXCEPTION
    WHEN OTHERS THEN
        NULL;  -- 로그 실패가 원래의 UPDATE를 막지 않도록
END;
```

`SYS_CONTEXT('USERENV', ...)`는 현재 세션의 환경 정보를 돌려준다. 여기서 필요한 것은 `IP_ADDRESS`였다. 어느 서버에서 붙었는지만 알면 되기 때문이다.

트리거를 건 이유는 하나다. **배치가 언제 도는지 몰라도, 도는 순간 스스로 기록을 남기기 때문이다.** 관찰자가 그 시각에 깨어 있을 필요가 없다.

### 지금이라면 행 단위로 걸지 않을 것이다

위 트리거는 `FOR EACH ROW`가 붙은 행 단위 트리거다. 그때는 그렇게 걸었다. 배치가 수만 건을 갱신하면 로그도 수만 건이 쌓이는데, 알고 싶은 것은 "누가 접속했는가"이지 "몇 건을 고쳤는가"가 아니었다. `FOR EACH ROW`를 빼고 문 단위로 걸면 UPDATE 한 번에 한 줄만 남고, 그것으로 충분했다. 개발 서버였고 확인 직후 지울 것이라 문제가 되지는 않았지만, 같은 방법을 다시 쓴다면 문 단위로 건다.

### 트리거를 걸기 전에 정한 것

트리거는 공짜가 아니다. 그 테이블의 모든 UPDATE에 따라붙는 코드다. 그래서 걸기 전에 세 가지를 정했다.

- **무엇만 남길 것인가.** 접속 정보만 적었다. 변경 전후 값까지 넣으면 로그가 금방 불어나고, 지금 필요한 것은 "누가"이지 "무엇을"이 아니었다.
- **실패해도 본 작업을 막지 않을 것.** 트리거 안에서 예외가 나면 원래의 UPDATE까지 실패한다. 그래서 로그 INSERT 실패는 삼키도록 했다.
- **언제 걷어낼 것인가.** 원인을 확인하는 순간 제거하기로 했고, 실제로 그렇게 했다. 진단용 코드를 남겨 두면 다음 사람에게는 왜 있는지 모르는 코드가 된다.

개발 서버라 응답 지연을 걱정하지 않고 걸 수 있었다. 운영 테이블이었다면 문 단위 트리거, 예외 삼킴, 즉시 제거는 선택이 아니라 필수였을 것이고, 걸기 전에 협의가 먼저였을 것이다.

자율 트랜잭션(`PRAGMA AUTONOMOUS_TRANSACTION`)을 쓰면 로그를 별도 트랜잭션으로 커밋할 수 있다. 배치가 롤백되어도 흔적은 남는다는 장점이 있다. 이번에는 갱신이 성공하고 있는 상황이었으므로 쓰지 않았다.

## 결과

로그가 쌓였고, `client_ip`는 하나의 주소를 가리켰다. **전환 이전 서버의 IP였다.**

IP를 기록한 것 자체는 기술이 아니다. 그 값을 보고 "이건 지금 서버가 아닌데"라고 알아본 것이 문제를 푼 지점이었다. 시스템 구성이 어떻게 바뀌어 왔는지 알고 있어야 나올 수 있는 판단이라, 로그만 쌓아 두고 넘겼다면 못 찾았을 것이다.

그 서버에 들어가 프로세스 목록을 보니, 내렸다고 알고 있던 옛 WAS 프로세스가 **정상 종료되지 않은 채 살아 있었다.** 종료 스크립트는 실행됐지만 프로세스가 끝까지 내려가지 않았고, 그 안의 스케줄러가 DB 세션을 유지한 채 배치를 계속 돌리고 있었다. "내렸다"는 인식과 실제 프로세스 상태가 달랐던 것이다.

```bash
ps -ef | grep java | grep -v grep
```

IP를 확보하고 나니 그다음은 단순했다. 프로세스를 확인하고 종료했다. 종료 뒤 로그 테이블에 더 이상 행이 쌓이지 않는 것을 보고 트리거를 제거했다.

## 무엇을 잘못 짚었는가

처음에 시간을 쓴 방향은 "배치가 어떻게 살아 있는가"였다. 컨테이너를 내렸는데 왜 도는지, 스케줄러 설정이 어디에 남아 있는지를 뒤졌다.

문제를 잘못 세웠다. 알아야 할 것은 **어디서 도는가**였다. 어디서 도는지를 먼저 알면 왜 도는지는 그 서버에 들어가서 확인하면 되는데, 순서를 반대로 잡고 있었다.

재현이 안 되는 문제에서 원인의 메커니즘부터 추론하려는 습관이 있는데, 이번 건은 위치를 먼저 특정하는 편이 훨씬 빨랐다. 추론 대신 관측이 가능한 지점을 만드는 쪽이 나은 경우가 있다.

## 그 뒤에 바꾼 것

- **종료 스크립트를 믿지 않는다.** 스크립트 실행 뒤 프로세스 목록으로 실제 종료를 교차 확인하는 것을 전환 절차에 넣었다.
- **옛 서버의 DB 접근을 회수한다.** 더 쓰지 않는 서버는 전원을 내리거나, 그게 안 되면 DB 쪽 접근 경로를 막아 둔다. 살아 있어도 DB에 닿지 못하면 이런 일은 생기지 않는다.
- 종료 스크립트가 프로세스를 끝까지 내리지 못한 이유는 스크립트 쪽 문제로 보고 보완 대상으로 남겼다.

## 정리

- 어디서 오는지 모르는 갱신은 로그를 볼 대상을 특정할 수 없어 일반적인 방법으로 추적되지 않는다.
- Oracle이라면 `v$session`의 `machine`·`program`을 먼저 본다. 커넥션 풀을 쓰는 WAS라면 거기에 잡힐 가능성이 크다. 이번에는 그 단계를 건너뛰었다.
- UPDATE 트리거와 `SYS_CONTEXT('USERENV', 'IP_ADDRESS')`로, 갱신이 일어나는 순간 스스로 출처를 남기게 할 수 있다. 관찰자가 그 시각에 깨어 있을 필요가 없다는 점이 이 방법의 핵심이다.
- 트리거는 접속 정보만, 실패는 삼키고, 확인 즉시 제거한다. 행 단위가 아니라 문 단위로 거는 편이 맞았다.
- 종료 명령을 내린 것과 프로세스가 실제로 내려간 것은 별개다. 전환 뒤에는 옛 서버의 프로세스 목록을 직접 확인한다.

가장 큰 교훈은 마지막 항목이었다. "내렸다"고 알고 있던 상태가 실제 상태와 달랐고, 그 차이를 확인할 방법이 없었다는 것이 문제의 본질이었다. 개발 서버에서 먼저 겪은 덕에 운영 전환 절차에 확인 단계를 넣을 수 있었다.
