> 명령어와 쿼리는 일반적인 형태다. 서버 구성과 실측값은 적지 않는다.

DB 서버의 파일시스템 사용률이 99%를 넘었다는 관제 알람을 받았다. 이런 알람을 받으면 보통 증설을 먼저 떠올린다. 그런데 **DB 서버에서는 알람이 떴다고 해서 실제로 공간이 부족한 것은 아니다.** 이 글은 그 알람을 받고 무엇을 확인했고, 왜 아무것도 하지 않는 쪽으로 결론이 났는지에 대한 기록이다.

## OS가 보는 용량과 DB가 쓰는 용량은 다르다

이게 핵심이다. Oracle 데이터파일은 **미리 크기를 잡아 두고, 그 안을 채워 나가는** 구조다.

한 테이블스페이스에 50GB짜리 데이터파일이 잡혀 있으면, 실제로 데이터가 10GB만 들어 있어도 **파일 크기는 50GB다.** OS는 50GB를 쓰고 있다고 보고, 파일시스템 사용률에도 그대로 반영된다. 관제는 OS 쪽 수치를 보고 울린다.

그래서 알람을 받으면 두 가지를 따로 봐야 한다.

```bash
# OS 관점 — 파일시스템 사용률
df -h          # 유닉스 계열에 따라 옵션 표기가 다르다
```

```sql
-- DB 관점 — 테이블스페이스별 할당량
SELECT tablespace_name, ROUND(SUM(bytes)/1024/1024) alloc_mb
  FROM dba_data_files
 GROUP BY tablespace_name;

-- DB 관점 — 그 안의 여유 공간
SELECT tablespace_name, ROUND(SUM(bytes)/1024/1024) free_mb
  FROM dba_free_space
 GROUP BY tablespace_name;
```

할당량과 여유 공간의 차이가 크면 **디스크가 부족한 게 아니라 안 쓰는 공간을 잡고 있는 것**이다.

## 두 가지 경우로 갈린다

확인 결과에 따라 조치가 달라진다. 같은 알람이라도 답이 반대일 수 있다.

| | 할당은 크고 실사용은 적을 때 | 테이블스페이스가 실제로 부족할 때 |
|---|---|---|
| 상황 | 파일은 크게 잡혀 있으나 내부에 여유가 많음 | 여유 공간이 실제로 소진됨 |
| 조치 | **당장 손대지 않음.** 증설도 축소도 필요 없음 | 데이터파일 추가로 공간 확보 |
| 이후 | 여유가 줄면 다른 볼륨에 공간을 할당하도록 정리 | 증가 추이를 보고 다음 임계치 대응 |

이번 건은 첫 번째 경우였다. 파일시스템은 거의 찼지만 테이블스페이스 안에는 여유가 충분했다. 그래서 **아무것도 하지 않는 것**이 답이었다. 알람이 떴으니 뭐라도 해야 한다는 압박에 데이터파일을 줄이거나 디스크를 늘리면, 실제 문제는 없는데 작업 리스크만 생긴다. 대신 판단과 근거를 남기고, 테이블스페이스 여유가 어느 수준 아래로 내려가면 다른 볼륨에 데이터파일을 추가한다는 다음 기준을 정해 두었다.

두 번째 경우였다면 기존 테이블스페이스에 데이터파일을 하나 더 붙이는 쪽을 골랐을 것이다.

```sql
ALTER TABLESPACE target_ts
  ADD DATAFILE '/path/to/datafile02.dbf' SIZE 10G;
```

기존 파일을 키우는 방법도 있지만, **파일을 하나 더 추가하면 다른 볼륨에 둘 수 있어서** 특정 파일시스템만 꽉 차는 상황을 피할 수 있다.

## 줄이는 건 생각보다 어렵다

> 아래는 직접 수행한 조치가 아니라, 축소를 검토하면서 확인한 제약이다.

데이터파일은 `RESIZE`로 줄일 수 있지만, **마지막 블록이 있는 지점보다 아래로는 줄지 않는다.**

```sql
ALTER DATABASE DATAFILE '/path/to/datafile01.dbf' RESIZE 20G;
```

파일 끝쪽에 블록 하나만 남아 있어도 그 앞까지는 유지된다. 데이터를 많이 지웠는데도 파일이 줄지 않는 것처럼 보이는 이유가 이것이다. 이럴 땐 세그먼트를 옮기는 재구성이 필요한데, 단순 정리보다 부담이 크다.

**축소는 마지막 수단으로 두는 편이 낫다.** 여유가 있다면 그대로 두고, 부족하면 파일을 추가하는 쪽이 리스크가 작다.

## 공간을 실제로 확보해야 한다면

두 번째 경우이고 파일을 추가할 볼륨도 없다면, 아래를 먼저 본다.

- **아카이브 로그.** 정리 정책이 없으면 계속 쌓인다. 백업 정책과 맞춰 보존 기간을 정하고 배치로 정리한다.
- **감사 로그·성능 이력.** 보존 기간이 길게 잡혀 있으면 과거 데이터가 상당한 공간을 차지한다.
- **대용량 세그먼트.** 임시 테이블이나 오래된 백업 테이블처럼 지워도 되는 것이 남아 있는지 본다.

## 정리

- **알람은 증상이지 원인이 아니다.** 파일시스템 사용률과 DB 실사용량을 각각 확인하기 전에는 무엇을 해야 할지 알 수 없다.
- Oracle 데이터파일은 미리 잡아 둔 크기로 OS에 보인다. OS 사용률 99%와 테이블스페이스 부족은 다른 말이다.
- **아무것도 하지 않는 것도 조치다.** 문제가 없다고 판단했으면 그 판단과 근거를 남기고, 다음 임계치에서 무엇을 할지 정해 둔다.
- **되돌리기 쉬운 쪽을 먼저 고른다.** 파일 추가는 되돌리기 쉽고, 축소나 재구성은 그렇지 않다.
