> 명령어와 쿼리는 일반적인 형태다. 서버 구성과 실측값은 적지 않는다.

DB 서버의 파일시스템 사용률이 99%를 넘었다는 관제 알람을 받았다. 이런 알람을 받으면 보통 증설을 먼저 떠올린다. 그런데 **파일시스템이 거의 찼다는 것과 테이블스페이스의 사용 가능한 공간이 부족하다는 것은 같은 말이 아니다.**

## OS가 보는 용량과 DB가 쓰는 용량은 다르다

Oracle 데이터파일은 미리 크기를 잡아 두고 그 안을 채워 나가는 구조다.

한 테이블스페이스에 50GB짜리 데이터파일이 잡혀 있으면, 실제로 데이터가 10GB만 들어 있어도 파일 크기는 50GB다. OS는 50GB를 쓰고 있다고 보고, 파일시스템 사용률에도 그대로 반영된다. 관제는 OS 쪽 수치를 보고 울린다.

그래서 알람을 받으면 두 가지를 따로 봐야 한다.

```bash
# OS 관점 — 파일시스템 사용률
df -h          # 유닉스 계열에 따라 옵션 표기가 다르다
```

```sql
-- DB 관점 — 테이블스페이스별 할당량
SELECT tablespace_name, ROUND(SUM(bytes)/1024/1024) alloc_mb
  FROM dba_data_files
 GROUP BY tablespace_name;

-- DB 관점 — 그 안의 여유 공간
SELECT tablespace_name, ROUND(SUM(bytes)/1024/1024) free_mb
  FROM dba_free_space
 GROUP BY tablespace_name;
```

할당량에 비해 여유 공간의 비율이 크면 데이터파일 안에 아직 세그먼트에 할당하지 않은 공간이 많이 남아 있는 것이다. `할당량 - 여유 공간`은 세그먼트 등에 할당된 공간이며, 실제 행 데이터의 크기와는 다르다. 세그먼트 안에도 재사용할 빈 공간이 있을 수 있다.

`DBA_FREE_SPACE`는 여유 익스텐트가 없으면 해당 파일의 행 자체를 반환하지 않는다. 위 두 조회 결과를 대조할 때 빠진 항목을 놓치면 안 된다. 오프라인 파일도 조회에서 빠질 수 있으므로 먼저 파일 상태를 확인한다. 이 조회는 영구 데이터파일 기준이며 TEMP 공간은 별도로 확인한다. [Oracle DBA_FREE_SPACE 문서](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/DBA_FREE_SPACE.html)

## 두 가지 경우로 갈린다

확인 결과에 따라 조치가 달라진다. 같은 알람이라도 답이 반대일 수 있다.

| | 할당은 크고 실사용은 적을 때 | 테이블스페이스가 실제로 부족할 때 |
|---|---|---|
| 상황 | 파일은 크게 잡혀 있으나 내부에 여유가 많음 | 여유 공간이 실제로 소진됨 |
| 조치 | 파일시스템의 추가 증가 요인까지 확인한 뒤 용량 변경 보류 | 여유 볼륨과 테이블스페이스 유형을 확인한 뒤 확장 방법 결정 |
| 이후 | 여유가 줄면 다른 볼륨에 공간을 할당하도록 정리 | 증가 추이를 보고 다음 임계치 대응 |

이번 건은 첫 번째 경우였다. 파일시스템은 거의 찼지만 테이블스페이스 안에는 여유가 충분했다. 그래서 **데이터파일을 줄이거나 디스크를 늘리지 않는 것**이 답이었다. 알람이 떴으니 뭐라도 해야 한다는 압박에 용량을 바로 바꾸면, 당장 해결할 DB 공간 문제는 없는데 작업 리스크만 생긴다. 대신 판단과 근거를 남기고, 테이블스페이스 여유가 어느 수준 아래로 내려가면 다른 볼륨에 데이터파일을 추가한다는 다음 기준을 정해 두었다.

물론 테이블스페이스 안에 여유가 있다는 이유만으로 파일시스템 99%를 무시해도 된다는 뜻은 아니다. 같은 파일시스템에 아카이브 로그·덤프·일반 로그가 계속 늘거나 데이터파일 자동 확장이 걸려 있다면 OS 공간 부족은 별도의 장애가 된다. DB 내부 여유와 파일시스템에서 앞으로 늘어날 파일을 함께 확인해야 용량 변경을 하지 않는 판단이 성립한다.

두 번째 경우였다면 기존 테이블스페이스에 데이터파일을 하나 더 붙이는 쪽을 골랐을 것이다.

```sql
ALTER TABLESPACE target_ts
  ADD DATAFILE '/path/to/datafile02.dbf' SIZE 10G;
```

위 예시는 smallfile 테이블스페이스 기준이다. bigfile 테이블스페이스는 데이터파일이 하나라 `ADD DATAFILE`을 사용할 수 없다. 기존 파일 확장이나 저장소 이동 등 별도 방법을 검토해야 한다. [Oracle 데이터파일 관리 문서](https://docs.oracle.com/en/database/oracle/oracle-database/26/admin/managing-data-files-and-temp-files.html)

기존 파일을 키우는 방법도 있지만, 파일을 하나 더 추가하면 다른 볼륨에 둘 수 있어서 특정 파일시스템만 꽉 차는 상황을 피할 수 있다.

## 줄이는 건 생각보다 어렵다

> 아래는 직접 수행한 조치가 아니라, 축소를 검토하면서 확인한 제약이다.

데이터파일은 `RESIZE`로 줄일 수 있지만, **마지막 블록이 있는 지점보다 아래로는 줄지 않는다.**

```sql
ALTER DATABASE DATAFILE '/path/to/datafile01.dbf' RESIZE 20G;
```

파일 끝쪽에 블록 하나만 남아 있어도 그 앞까지는 유지된다. 데이터를 많이 지웠는데도 파일이 줄지 않는 것처럼 보이는 이유가 이것이다. 이럴 땐 세그먼트를 옮기는 재구성이 필요한데, 단순 정리보다 부담이 크다.

축소는 마지막 수단으로 두는 편이 낫다. 여유가 있다면 그대로 두고, 부족하면 파일을 추가하는 쪽이 리스크가 작다.

## 공간을 실제로 확보해야 한다면

두 번째 경우이고 파일을 추가할 볼륨도 없다면, 아래를 먼저 본다.

- **아카이브 로그.** 백업·복구와 복제에 필요한 로그인지 먼저 확인한다. RMAN의 보존·삭제 정책에 맞춰 관리하며, 파일을 임의로 지우는 방식으로 공간을 확보하지 않는다.
- **감사 로그·성능 이력.** 보존 기간이 길게 잡혀 있으면 과거 데이터가 상당한 공간을 차지한다.
- **대용량 세그먼트.** 임시 테이블이나 오래된 백업 테이블처럼 지워도 되는 것이 남아 있는지 본다.

테이블의 행이나 세그먼트를 정리해 생긴 DB 내부 여유는 파일시스템의 여유로 바로 돌아가지 않는다. OS 공간을 확보하려는 것인지, 기존 데이터파일 안에서 재사용할 공간을 확보하려는 것인지 구분한다.

## 정리

- 파일시스템 사용률과 테이블스페이스 여유는 다른 수치다. 둘을 따로 확인하기 전에는 증설인지 보류인지 정할 수 없다.
- 용량을 바꾸지 않는 것도 조치다. 바꾸지 않기로 했으면 근거와 다음 임계치에서 할 일을 남긴다.
- 공간이 실제로 부족하면 파일 추가가 축소나 세그먼트 재구성보다 단순하다. 다만 추가한 파일도 안에 세그먼트가 생기면 쉽게 제거되지 않는다.
