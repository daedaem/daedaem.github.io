**한 줄 요약.** HTTPS 연결이 핸드셰이크에서 막히고 메시지가 암호 관련으로 보인다면, 코드보다 **클라이언트 런타임의 버전**을 먼저 본다. 오래된 JDK는 요즘 서버가 요구하는 TLS 버전과 키 길이를 처리하지 못한다.

## 에러가 원인을 안 알려준다

이런 메시지들이 나온다.

```
Could not generate DH keypair
Received fatal alert: handshake_failure
The server selected protocol version TLS10 is not accepted
```

첫 줄만 보면 키 생성 로직이 잘못된 것 같지만, 실제로는 대부분 **클라이언트가 서버의 요구 수준을 따라가지 못해서** 생긴다. 핸드셰이크는 양쪽이 쓸 수 있는 프로토콜과 암호 방식을 맞추는 단계라, 겹치는 것이 없으면 연결 자체가 성립하지 않는다.

## 버전별로 갈리는 지점

| | 기본 TLS | DH 키 길이 |
|---|---|---|
| JDK 6 | TLS 1.0 | 1024비트 초과 처리 불가 |
| JDK 7 | TLS 1.0 (1.2는 옵션으로 활성화) | 2048비트 지원 |
| JDK 8 이상 | TLS 1.2 | 제약 없음 |

요즘 서버는 보통 **TLS 1.2 이상만 허용**하고 **2048비트 DH 파라미터**를 내려준다. 그러면 오래된 클라이언트는 두 가지 모두에서 걸린다. `Could not generate DH keypair`는 두 번째 항목, `protocol version TLS10 is not accepted`는 첫 번째 항목이 원인이다.

JDK 7은 TLS 1.2를 지원하지만 기본값이 아니다. `https.protocols`·`jdk.tls.client.protocols` 시스템 속성이나 `SSLContext.getInstance("TLSv1.2")`로 명시해야 쓴다. 즉 **JDK 7이면 설정으로 넘어갈 여지가 있고, JDK 6이면 런타임의 한계**다.

## 서버 쪽을 낮추는 것은 답이 아니다

상대에게 TLS 1.0을 허용해 달라거나 키 길이를 낮춰 달라고 요청할 수도 있다. 하지만 그 설정은 보안 때문에 올린 것이고, 낮추면 그 서버에 붙는 **모든** 클라이언트의 보안 수준이 함께 내려간다. 우리 쪽 사정으로 남의 보안 기준을 되돌리는 요청은 하지 않는 편이 맞다.

## 런타임을 올릴 수 없을 때의 선택지

1. **런타임 업그레이드.** 정답이다. 다만 오래된 시스템은 런타임·WAS·프레임워크·라이브러리가 서로 묶여 있어 하나만 올리기 어려운 경우가 많다.
2. **통신 부분만 분리.** 외부 통신을 담당하는 작은 모듈만 상위 버전 런타임으로 띄우고 기존 시스템과 연결한다. 관리할 것이 하나 늘어난다.
3. **이미 있는 경로 경유.** 같은 목적지에 닿는 경로가 이미 있다면 새로 만들지 않고 그것을 쓴다. 만드는 것이 없으니 리스크가 가장 작다.

## 무엇을 기준으로 고르나

- 이 기능 하나 때문에 **시스템 전체의 런타임을 올리는 것이 맞는가.** 올린다면 회귀 범위는 어디까지이고, 같은 런타임을 쓰는 기능이 몇 개인가.
- 대안 경로가 **임시방편인가, 구조적으로 안정적인가.**
- 우회를 골랐다면 **왜 그렇게 했는지를 남긴다.** 나중에 런타임을 올릴 때 무엇을 걷어내면 되는지가 그 기록에서 나온다.

## 정리

- 핸드셰이크 실패 메시지는 암호 로직이 아니라 런타임 버전을 먼저 의심한다.
- JDK 6은 기본 TLS 1.0에 DH 1024비트 제약이 있어 요즘 서버에 붙지 못한다. JDK 7은 TLS 1.2를 설정으로 켤 수 있다.
- 서버의 보안 수준을 낮춰 달라는 요청은 하지 않는다.
- 런타임을 못 올리면 통신 모듈 분리나 기존 경로 경유가 선택지이고, 어느 쪽이든 이유를 기록으로 남긴다.
