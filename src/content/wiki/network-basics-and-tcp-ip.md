## 네트워크를 재는 말들

네트워크는 **노드와 링크의 집합체**다. 성능을 이야기할 때 쓰는 용어부터 정리한다.

| 용어 | 뜻 |
|---|---|
| **처리량(throughput)** | 단위 시간당 데이터 양. 단위는 bps |
| **트래픽** | 특정 시점에 링크를 흐르는 데이터 양 |
| **대역폭(bandwidth)** | 주어진 시간 동안 흐를 수 있는 **최대** 비트 수 |
| **지연 시간(latency)** | 데이터가 출발지에서 목적지까지 전달되는 데 걸리는 시간. 전파·전송·큐잉·장비 처리 지연에 좌우 |

### 토폴로지와 병목

노드와 링크를 어떻게 배치하느냐가 토폴로지다. **토폴로지를 아는 이유는 병목을 찾을 때 기준이 되기 때문**이다.

| 형태 | 특징 | 약점 |
|---|---|---|
| 트리 | 계층형. 노드 추가·삭제 쉬움 | 특정 노드에 트래픽이 몰리면 하위가 영향받음 |
| 버스 | 중앙 회선 하나를 공유. 설치 비용 낮음 | **스푸핑**에 취약 |
| 스타 | 중앙 노드에 전부 연결. 충돌 적고 장애 탐지 쉬움 | **중앙이 죽으면 전체가 죽음** |
| 링 | 양옆 두 노드와 연결 | 회선 장애가 전체에 영향 |
| 메시 | 그물망. 경로가 여러 개라 장애에 강함 | 구축·운용 비용이 큼 |

병목 현상은 **전체 성능이 하나의 구성 요소 때문에 제한되는 것**이다. 원인은 보통 대역폭, 토폴로지, 서버 CPU·메모리, 비효율적 구성 넷 중 하나다.

### 규모로 나눈 분류

**LAN**(개인·사무실, 빠르고 덜 혼잡) → **MAN**(도시) → **WAN**(국가·대륙, 느리고 혼잡).

### 진단 명령

코드에 문제가 없는데 데이터를 못 가져오면 네트워크를 의심한다.

| 명령 | 무엇을 보나 |
|---|---|
| `ping` | 대상 노드까지 패킷이 가는지, 얼마나 걸리는지. **ICMP 기반이라 차단된 대상에는 못 씀** |
| `netstat` | 현재 접속·라우팅 테이블·프로토콜 상태 |
| `nslookup` | 도메인에 매핑된 IP |
| `tracert` / `traceroute` | 목적지까지의 경로와 **어느 구간이 느린지** |

## IP — 그리고 그 한계

IP는 인터넷에서 데이터를 주고받는 규약이다. 하는 일은 두 가지다.

- 지정한 IP 주소로 데이터를 전달한다
- **패킷**이라는 단위로 쪼개서 보낸다 (출발지 IP, 목적지 IP, 전송 데이터 등이 담긴다)

중간 노드들이 목적지가 어디인지 서로 물어가며 패킷을 넘긴다. 이게 라우팅이다.

문제는 IP만으로는 부족하다는 것이다. **세 가지 한계가 있다.**

**비연결성** — 받을 대상이 없거나 서비스 불능이어도 그냥 보낸다. 보내는 쪽은 상대가 받을 수 있는 상태인지 모른다.

**비신뢰성** — 중간 노드나 혼잡 때문에 패킷이 사라지거나 중복되고, 서로 다른 경로를 거치며 순서가 바뀔 수 있다. 링크의 MTU보다 큰 IPv4 패킷은 경로와 설정에 따라 조각화될 수도 있다. TCP는 이런 IP 위에서 손실과 순서 변경을 처리한다.

**프로그램 구분 불가** — IP 주소는 호스트 주소다. 같은 서버에서 애플리케이션이 둘 이상 돌면 구분할 수 없다.

## TCP — 한계를 메우는 방법

| 특징 | 어떻게 |
|---|---|
| **연결 지향** | 3-way handshake로 가상 연결을 먼저 맺는다 |
| **전달 보증** | 받으면 **ACK**로 확인 응답을 보낸다 |
| **순서 보장** | ACK 번호는 보통 "다음에 받을 바이트"를 나타낸다. 수신 측은 SEQ로 순서를 맞추고, 송신 측은 타임아웃이나 중복 ACK 같은 신호를 바탕으로 손실된 구간을 재전송한다 |
| **흐름 제어** | 송신·수신 측의 처리 속도 차이를 조절 |
| **혼잡 제어** | 네트워크 내 패킷 수가 넘치지 않게 방지 |

### UDP는 반대편

기능이 거의 없다. 연결 지향도, 전달 보증도, 순서 보장도 없다. IP에 **PORT와 checksum 정도만** 얹은 것이다. 대신 단순하고 빠르다. 필요한 보증은 애플리케이션이 직접 구현해야 한다.

## PORT와 DNS

**PORT**가 IP의 세 번째 한계(프로그램 구분)를 푼다. IP가 아파트라면 PORT는 동·호수다.

- 0~65535 사용 가능
- **0~1023은 잘 알려진 포트**라 피한다. HTTP 80, HTTPS 443

**DNS**는 도메인 이름을 IP로 바꿔준다. IP는 외우기 어렵고 바뀔 수 있어서 전화번호부 같은 계층이 필요하다.

## 3-way handshake — 연결 맺기

```
클라이언트 ──── SYN ────▶ 서버
클라이언트 ◀── SYN+ACK ── 서버
클라이언트 ──── ACK ────▶ 서버
```

일반적인 TCP 연결은 이 과정이 끝난 뒤 애플리케이션 데이터를 보낸다. 다만 핸드셰이크 성공은 해당 포트까지 연결됐다는 뜻일 뿐, 애플리케이션과 그 뒤의 DB까지 정상이라는 보장은 아니다.

두 가지를 짚어둘 만하다.

**논리적 연결이지 물리적 연결이 아니다.** 두 종단만 "연결됐다"고 알고 있을 뿐, 중간의 수많은 노드는 그 사실을 모른다. 전용 회선이 보장되는 게 아니다.

마지막 ACK에 데이터를 실어 보내는 것은 원래부터 허용된 동작이다. SYN 단계부터 데이터를 싣는 최적화는 따로 TCP Fast Open이라고 부른다.

## 4-way handshake — 연결 끊기

```
클라이언트 ──── FIN ────▶ 서버
클라이언트 ◀─── ACK ───── 서버   (CLOSE_WAIT — 남은 데이터를 마저 보낸다)
클라이언트 ◀─── FIN ───── 서버
클라이언트 ──── ACK ────▶ 서버   (TIME_WAIT — 늦게 오는 데이터를 기다린다)
```

닫을 때 4번인 이유는 **서버가 아직 보낼 데이터가 남아 있을 수 있기 때문**이다. FIN을 받고 바로 닫지 않고 ACK만 먼저 보낸 뒤(CLOSE_WAIT), 다 보내고 나서 자기 FIN을 보낸다.

능동적으로 연결을 닫은 쪽의 `TIME_WAIT`은 지연된 중복 세그먼트가 다음 연결에 섞이는 것을 막고, 마지막 ACK가 유실되면 다시 보내기 위한 대기다. 서버에 `CLOSE_WAIT`이 계속 쌓여 있다면 상대의 FIN을 받은 뒤 **애플리케이션이 소켓 닫기를 완료하지 못하고 있다는 신호**다.

## TCP/IP 4계층

데이터를 보낼 때는 위에서 아래로 내려가며 계층마다 헤더가 붙고(**캡슐화**), 받을 때는 아래에서 위로 올라가며 헤더를 읽고 떼어낸다(**역캡슐화**).

| 계층 | 하는 일 | 프로토콜 |
|---|---|---|
| **애플리케이션** | 사용자·소프트웨어 간 소통 | HTTP, HTTPS, FTP, SSH, DNS, SMTP |
| **전송** | 통신 노드 간 신뢰성 보장. **포트로 올바른 앱에 전달** | TCP, UDP |
| **인터넷** | 패킷을 최종 목적지까지 라우팅 | IP, ARP, ICMP |
| **네트워크 액세스** | 전기신호로 변환, **MAC 주소**로 전달 | Ethernet, Wi-Fi, PPP |

**TCP/IP**란 이 둘의 묶음이다. IP로 최대한 빠르게 보내고, TCP로 제대로 받았는지 챙긴다.
