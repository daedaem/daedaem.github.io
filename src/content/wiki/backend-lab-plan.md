> 계획 문서다. 아직 만든 것은 없고, 만들면서 이 문서를 고쳐 간다.

## 왜 블로그와 따로 만드는가

이 블로그는 정적이다. 글은 마크다운과 git에 있고 서버가 없다. 그래서 죽지 않고, 서비스에 종속되지 않는다. 지원서에 링크가 들어가는 곳이므로 이 성질은 지켜야 한다.

그런데 사이트에서 직접 글을 쓰고 고치고 지우려면 인증, 에디터, DB, 파일 업로드가 필요하다. 이건 정적 사이트에 얹을 수 있는 것이 아니라 하나의 웹 애플리케이션이다. 그리고 그 애플리케이션을 만드는 일 자체가 백엔드 포트폴리오가 된다.

둘을 합치면 블로그가 앱과 운명을 같이한다. 나누면 앱이 죽어도 블로그는 멀쩡하고, 앱은 마음껏 부수고 고칠 수 있다.

역할을 정리하면 이렇다.

| | 이 블로그 | 실험실 앱 |
|---|---|---|
| 성격 | 명함. 완성된 글과 설명 | 프로젝트. 만들고 부수고 측정하는 곳 |
| 글 저장 | 마크다운 + git | DB |
| 서버 | 없음 (GitHub Pages) | 있음 |
| 죽으면 | 지원서 링크가 죽는다 | 블로그에는 영향 없음 |
| 트래픽 | 실제 방문자 (적다) | 직접 만든 부하 + 실제 방문자 |

## 대용량 트래픽에 대한 전제

개인 블로그에는 처리할 대용량 트래픽이 없다. 하루 수십 명이다. "버틴다"는 주장은 검증할 수 없어서 아무도 믿지 않는다.

트래픽 처리 역량은 트래픽이 와서 증명되는 것이 아니라 **직접 부하를 걸고 측정한 숫자**로 증명된다. k6나 Gatling은 방문자가 10명이어도 초당 수천 요청을 만들어 준다. 그 결과를 글로 쓰는 것이 포트폴리오다. 채용 담당자가 보는 것은 가동률이 아니라 "무엇을 어떻게 측정하고 어떤 판단을 했는가"다.

## 구성

세 층이다.

```
[이 블로그 (정적)]  ──JS 호출──▶  [실험실 API]  ──▶  [DB / Redis]
                                       ▲
[실험실 관리 화면 (글 CRUD)] ───────────┘
                                       ▲
[k6 부하 스크립트] ─────────────────────┘
```

- **실험실 API** — Spring Boot 3, Java 21, JPA. 글 CRUD, 인증, 조회수·좋아요·댓글.
- **관리 화면** — 로그인해서 글을 쓰고 고치는 곳. React. 처음에는 최소 범위.
- **블로그와의 연결** — 블로그 글 페이지가 자바스크립트로 API를 불러 조회수·좋아요·댓글을 보여 준다. API가 죽으면 그 숫자만 안 보이고 글은 그대로다.
- **부하 스크립트** — k6. 실험마다 스크립트를 저장소에 남긴다.

### 실험실 앱에서 쓴 글을 블로그로 가져올 것인가

가져오지 않는다. 실험실 앱의 글은 실험 대상 데이터다. 블로그에 남길 만한 글은 마크다운으로 옮겨 git에 넣는다. 두 곳의 글이 자동으로 동기화되는 구조는 만들지 않는다. 그 동기화 자체가 장애 지점이 되고, 블로그의 "git이 원본"이라는 성질을 깨기 때문이다.

## 스택 결정과 고르지 않은 것

| 항목 | 고른 것 | 고르지 않은 것과 이유 |
|---|---|---|
| 언어·프레임워크 | Java 21, Spring Boot 3 | NestJS — 익숙하지 않은 것을 새로 배우는 것이 목적이 아니다. 이직 대상 스택에서 깊이를 보여 주는 것이 목적이다 |
| DB | PostgreSQL | MySQL — 큰 차이는 없다. 이미 개인 프로젝트에서 PostgreSQL을 쓰고 있어 맞춘다 |
| 캐시 | Redis (실험 단계에서 도입) | 처음부터 넣지 않는다. 없을 때 숫자를 먼저 재고, 넣어서 달라지는 것을 글로 쓴다 |
| 인증 | JWT, 관리자 1인 | OAuth — 사용자가 본인 하나뿐인 앱에 과하다. 댓글 작성자 인증이 필요해지면 그때 검토 |
| 배포 위치 | Oracle Cloud 무료 티어 또는 월 5천 원대 VPS | 관리형 PaaS — 운영을 직접 겪는 것이 목적이라 서버를 직접 만진다. 비용 상한은 월 1만 원 |
| 부하 도구 | k6 | Gatling — 스크립트가 JS라 빠르게 쓸 수 있다. JMeter는 무겁다 |
| 관측 | Spring Actuator + Prometheus + Grafana | 처음에는 Actuator만. 실험이 시작되면 Prometheus를 붙인다 |

## 첫 마일스톤

작게 시작한다. 이 단계에서 인프라를 만지느라 몇 주를 쓰지 않도록 한다.

1. **조회수 카운터 하나.** API 하나, 테이블 하나, 블로그 글 페이지에 숫자 하나. 배포까지.
2. 관리자 로그인과 글 CRUD. 에디터는 마크다운 textarea로 시작한다.
3. 좋아요 (멱등성이 필요한 첫 기능).
4. 댓글.

1번이 끝나면 아래 실험이 전부 이어진다.

## 실험 주제 (글로 쓸 것)

모두 어떤 규모에서든 재현 가능하다.

- 조회수 카운터를 DB `UPDATE`로 만들었을 때와 Redis `INCR` + 주기적 flush로 바꿨을 때의 p99와 처리량
- 좋아요 API에 멱등 키를 넣기 전후, 재시도 폭주에서 중복 반영 건수
- 캐시 만료 순간에 요청을 몰아넣어 캐시 스탬피드를 일으키고, 락·조기 갱신으로 막기
- 커넥션 풀 크기를 바꿔 가며 처리량이 꺾이는 지점 찾기
- 인기 글 상위 N 조회를 매번 집계할 때와 미리 계산해 둘 때
- 한 서버에서 GC 설정에 따라 지연 시간 분포가 어떻게 달라지는가
- 부하 중 배포 (무중단 배포가 실제로 무중단인지)

각 실험은 "가설 → 측정 방법 → 숫자 → 판단 → 고르지 않은 대안" 순서로 쓴다. 이 블로그의 글쓰기 원칙과 같다.

## 지금 하지 않는 것

- 블로그를 동적으로 바꾸는 것
- 두 곳 글의 자동 동기화
- 처음부터 Redis, 큐, 컨테이너 오케스트레이션을 넣는 것. 없을 때의 숫자가 먼저다
- 이직 준비 기간에 이 일에 몇 주를 쓰는 것. 1번 마일스톤까지만 하고, 나머지는 이직 후에 한다

## 관련

- 개인 프로젝트에서 이미 다룬 것: 멱등 이체와 비관적 락(asset-ledger-api), 상태 전이 단일화(StablePay), DB 제약으로 예약 경합 차단(GymSpot). 실험실의 좋아요·댓글에서 그대로 쓴다.
