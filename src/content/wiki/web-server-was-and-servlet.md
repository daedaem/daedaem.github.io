## 웹 서버와 WAS

둘 다 HTTP 기반으로 동작한다. 차이는 **무엇을 돌려주느냐**다.

| | 웹 서버 | WAS |
|---|---|---|
| 주 역할 | 정적 리소스 (HTML, CSS, JS, 이미지, 영상) | 애플리케이션 로직 실행 |
| 결과물 | 파일 그대로 | 동적 HTML, HTTP API(JSON) |
| 예 | Apache, Nginx, IIS, WebtoB | Tomcat, Jetty, Undertow, JEUS, JBoss |

경계가 딱 떨어지지는 않는다. 웹 서버도 플러그인으로 프로그램을 돌릴 수 있고, WAS도 정적 리소스를 서빙한다. **자바에서는 서블릿 컨테이너 기능을 제공하면 WAS라고 부른다.**

## 왜 둘을 나누는가

WAS와 DB만으로도 시스템은 돌아간다. 그런데 세 가지 문제가 있다.

- WAS가 정적 리소스까지 다 처리하느라 부하가 몰린다
- 가장 비싼 자원인 애플리케이션 로직이 정적 리소스 때문에 밀린다
- **WAS가 죽으면 오류 화면조차 못 띄운다**

그래서 앞에 웹 서버를 둔다. 정적 리소스는 웹 서버가 처리하고, 동적 처리만 WAS로 넘긴다.

```
클라이언트 → 웹 서버 → WAS → DB
             (정적)   (로직)
```

이 구조의 이득이 두 가지다.

**증설을 따로 할 수 있다.** 정적 트래픽이 많으면 웹 서버를, 로직이 무거우면 WAS를 늘린다.

**장애 화면을 띄울 수 있다.** 애플리케이션 로직이 도는 WAS는 잘 죽지만, 정적 리소스만 주는 웹 서버는 잘 안 죽는다. WAS나 DB가 죽어도 웹 서버가 오류 페이지를 내보낼 수 있다.

## 서블릿

서블릿이 없다면 HTTP 요청 하나를 처리하기 위해 이걸 다 직접 짜야 한다 — 소켓 연결, HTTP 요청 메시지 파싱, 메서드/URL/헤더/바디 해석, 응답 메시지 생성, 소켓 종료.

서블릿을 지원하는 WAS를 쓰면 개발자는 **의미 있는 비즈니스 로직만** 짜면 된다.

```java
@WebServlet(name = "helloServlet", urlPatterns = "/hello")
public class HelloServlet extends HttpServlet {
    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) {
        // 애플리케이션 로직만
    }
}
```

- `urlPatterns`의 URL이 호출되면 이 서블릿이 실행된다
- `HttpServletRequest`로 요청 정보를 꺼내고, `HttpServletResponse`에 응답을 담는다

### 요청 한 건의 흐름

1. HTTP 요청이 오면 WAS가 `Request`, `Response` 객체를 **새로 만들어** 서블릿을 호출한다
2. 개발자는 `Request`에서 필요한 값을 꺼낸다
3. 개발자는 `Response`에 응답을 담는다
4. WAS가 `Response`의 내용으로 HTTP 응답 메시지를 만들어 보낸다
5. 응답이 끝나면 두 객체를 소멸시킨다

### 서블릿 컨테이너

톰캣처럼 서블릿을 지원하는 WAS를 서블릿 컨테이너라고 부른다. 하는 일은 서블릿 객체의 **생성·초기화·호출·종료**, 즉 생명주기 관리다.

여기서 반드시 알아야 할 게 하나 있다.

> **서블릿 객체는 싱글톤으로 관리된다.**

요청마다 객체를 새로 만드는 건 비효율이라, 최초 로딩 시점에 만들어두고 재사용한다. 즉 **모든 사용자의 요청이 같은 인스턴스에 접근한다.**

그래서 **공유 변수를 조심해야 한다.** 서블릿의 인스턴스 필드에 사용자 정보를 담아두면, 다른 사람의 요청이 그 값을 덮어쓰거나 읽어 간다. 로그인 상태에서 남의 계정 정보가 보이는 사고가 이렇게 난다.

JSP도 결국 서블릿으로 변환되어 실행된다.

## 동시 요청과 스레드

스레드는 애플리케이션 코드를 실행하는 주체다. 자바 `main` 메서드를 실행하면 `main`이라는 이름의 스레드가 돈다. **스레드 하나는 한 번에 한 줄만 실행하므로**, 동시에 처리하려면 스레드가 더 필요하다.

### 요청마다 스레드를 만들면

| 장점 | 단점 |
|---|---|
| 동시 요청 처리 가능 | **스레드 생성 비용이 비싸다** → 응답이 느려짐 |
| 리소스가 허용하는 한 최대 활용 | 컨텍스트 스위칭 비용 |
| 한 스레드가 지연돼도 나머지는 정상 | **제한이 없어 요청이 몰리면 서버가 죽는다** |

### 그래서 스레드 풀

미리 만들어 둔 스레드를 풀에 보관하고 빌려 쓴다.

- 필요하면 풀에서 꺼내 쓰고, 끝나면 반납한다
- 풀이 비면 요청을 **거절하거나 대기**시킨다
- **톰캣은 최대 200개가 기본값**이다

이득은 두 가지다. 생성·종료 비용이 사라져 응답이 빨라지고, 최대치가 정해져 있어 요청이 몰려도 기존 요청은 안전하게 처리된다.

적정 개수는 정답이 없다. 로직 복잡도, CPU, 메모리, I/O 상황에 따라 다르다. **실제 서비스와 비슷한 조건으로 성능 테스트를 해서 정하는 게 맞다.** (Apache AB, JMeter, nGrinder)

### 개발자가 신경 쓸 것

멀티 스레드 처리는 WAS가 알아서 한다. 덕분에 싱글 스레드 프로그램을 짜듯 편하게 개발할 수 있다.

**단, 싱글톤 객체는 조심해야 한다.** 서블릿과 스프링 빈이 여기에 해당한다. 상태를 가지면 요청끼리 섞인다.
