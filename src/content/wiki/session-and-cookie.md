**한 줄 요약.** 세션은 서버가 가진 사물함이고, 세션 쿠키는 브라우저가 가진 열쇠다. 로그인 이후의 모든 요청은 이 열쇠 하나로 신원을 증명한다. 그래서 로그인 요청의 암호화보다 이 열쇠를 지키는 것이 더 중요하다.

## 세션과 쿠키의 관계

HTTP는 요청마다 연결이 끊기는 프로토콜이다. 서버는 방금 요청한 사람과 지금 요청한 사람이 같은 사람인지 기본적으로 알 수 없다.

그래서 서버가 **번호표**를 하나 넘기고, 브라우저는 그것을 요청마다 다시 내밀어 보인다.

```
  서버 메모리                        브라우저
┌────────────────────┐
│ 세션 "A1B2C3"        │  ←─  Cookie: JSESSIONID=A1B2C3
│   authState = ...  │
│   userSeq   = ...  │       번호표만 가지고 있음
└────────────────────┘       내용물은 모름
   내용물은 여기 있음
```

세션의 실제 데이터는 전부 서버에 있다. 브라우저가 가진 것은 **식별자 문자열 하나뿐**이다.

## 왜 코드에서 쿠키 생성부를 못 찾는가

**개발자가 작성하는 코드가 아니기 때문이다.** 서블릿 컨테이너(WAS)가 처리한다.

```java
HttpSession session = request.getSession();
```

이 호출 시점에 WAS가 하는 일은 이렇다.

1. 요청에 `JSESSIONID` 쿠키가 있는가?
2. 없다 → 랜덤 세션 ID 생성 → 메모리에 세션 객체 생성
3. 응답 헤더에 자동으로 쿠키를 싣는다. `Set-Cookie: JSESSIONID=A1B2C3D4; Path=/`
4. 브라우저가 저장 → 이후 모든 요청에 자동 첨부

JSP는 페이지 지시자의 `session` 속성 기본값이 `true`라 기본적으로 `getSession()`을 부른다. **페이지를 열기만 해도 세션이 생긴다.**

## 흔한 오해 — getSession() 호출마다 세션이 생긴다?

**틀렸다.** 세션은 브라우저당 하나만 만들어진다.

`getSession()`은 "세션을 만들어라"가 아니라 **"내 세션을 가져와라, 없으면 만들어라"**다.

```
[첫 요청] 쿠키 없음
   getSession() → 신규 생성 → Set-Cookie 응답에 실림   ★ 딱 한 번

[두 번째 요청] Cookie: JSESSIONID=A1B2C3
   getSession() → 기존 세션 반환 → Set-Cookie 없음

[세 번째 ~ 백 번째 요청]
   getSession() → 매번 같은 세션 반환 → Set-Cookie 없음
```

코드 100군데에서 불러도 **세션은 하나**이고 쿠키도 처음 한 번만 발급된다. 사물함 열쇠를 처음 한 번 받고, 그 뒤로는 계속 같은 열쇠로 같은 칸을 여는 것과 같다.

### 세션 유지와 세션 안의 값 유지는 다르다

세션은 유지되더라도, 그 안의 값은 코드가 덮어쓰면 바뀐다.

```java
// (A) 가드 없음 — 호출할 때마다 값이 바뀐다
session.setAttribute("token", newToken());

// (B) 가드 있음 — 처음 한 번만
if (session.getAttribute("token") == null) {
    session.setAttribute("token", newToken());
}
```

(A)라면 탭을 여러 개 열었을 때 나중 탭이 앞 탭의 값을 덮어쓴다. 세션은 하나인데 화면은 여러 개이기 때문이다.

## 세션이 새로 생기는 경우

| 상황 | 이유 |
|---|---|
| 브라우저 완전 종료 후 재접속 | 세션 쿠키는 만료일이 없어 브라우저 종료 시 삭제된다 |
| 세션 타임아웃 경과 | 서버가 세션 객체를 정리한다 |
| `session.invalidate()` 호출 | 로그아웃, 세션 고정 방어 등 |
| 다른 브라우저 / 시크릿 창 | 쿠키 저장소가 별개다 |

## 왜 세션 쿠키가 가장 값비싼 자산인가

서버는 매 요청마다 아이디·비밀번호를 다시 확인하지 않는다. **쿠키만 보고 판단한다.** 그러므로 쿠키를 가진 사람은 **로그인 절차를 건너뛰고** 그 사용자가 된다.

| 보호 범위 | 로그인 요청의 암호화 | 세션 쿠키 |
|---|---|---|
| 로그인 요청 1건 | 보호됨 | — |
| **로그인 이후 세션 전체** | **무관** | **이것 하나에 달려 있다** |

금고 다이얼을 아무리 복잡하게 만들어도, 열려 있는 금고 앞의 출입증을 훔치면 그만이다.

## 탈취 경로와 방어

| 경로 | 설명 | 방어 |
|---|---|---|
| 네트워크 도청 | HTTP면 쿠키가 평문으로 오간다. 공유 와이파이나 사내망에서 패킷만 잡으면 보인다 | HTTPS 강제 + `Secure` |
| XSS | 입력값에 스크립트를 심어 두면 다른 사용자 브라우저에서 `document.cookie`를 읽는다 | `HttpOnly` + 출력 이스케이핑 |
| 물리적 접근 | 공용 PC에서 로그아웃하지 않음, 개발자도구로 복사 | 짧은 타임아웃, 로그아웃 안내 |
| 세션 고정 | 공격자가 미리 심은 세션 ID가 그대로 인증된 세션이 된다 | 로그인 성공 시 세션 ID 재발급 |

## 쿠키 속성 세 가지

| 속성 | 효과 | 없으면 |
|---|---|---|
| `Secure` | HTTPS 요청에만 쿠키를 싣는다 | HTTPS 사이트라도 이미지 하나를 `http://`로 불러오면 그 요청에 쿠키가 딸려 나간다 |
| `HttpOnly` | JS가 쿠키를 읽지 못한다 | XSS 한 번이면 세션이 통째로 털린다 |
| `SameSite` | 다른 사이트에서 오는 요청에 쿠키를 제한한다 | CSRF 가능성이 커진다. 구버전 WAS는 미지원일 수 있다 |

설정 위치는 `web.xml`(Servlet 3.0 이상)이거나 WAS 설정 파일이다.

```xml
<session-config>
    <cookie-config>
        <http-only>true</http-only>
        <secure>true</secure>
    </cookie-config>
</session-config>
```

**둘 다 없으면 속성 없이 발급되고 있다고 보면 된다.**

## 적용 순서 — 반대로 하면 장애

`secure=true`를 먼저 켜면 **HTTP 접속 시 쿠키가 아예 실리지 않는다.** HTTP로 들어오는 사용자가 있으면 로그인이 안 되는 장애로 이어진다.

1. HTTP → HTTPS 강제 리다이렉트
2. 정상 동작 확인 (모든 진입 경로, 외부 링크 포함)
3. 그 다음 `secure=true`
4. HSTS 헤더 (되돌리기 어려우므로 마지막)

`HttpOnly`는 순서와 무관하게 먼저 켜도 된다. 단, **JS가 세션 쿠키를 직접 읽는 코드가 있는지**만 확인한다. 레거시에서 간혹 있다.

## 확인 방법

브라우저 개발자도구의 Network 탭에서 사이트에 접속해 본다.

- **첫 요청 응답 헤더에만** `Set-Cookie: JSESSIONID=...`가 있는가
- 그 뒤 요청들에는 없는가 (있으면 세션이 계속 새로 생기고 있다는 뜻)
- 쿠키 값 뒤에 `Secure`, `HttpOnly`가 붙어 있는가
- Application 탭의 Cookies에서 체크박스로도 확인할 수 있다

## 자주 헷갈리는 것

**세션은 서버에 있다면서 왜 브라우저가 영향을 받나.** 세션 데이터는 서버에 있지만, 그 세션을 찾을 수 있는 열쇠는 브라우저가 가지고 있다. 열쇠를 잃으면(브라우저 종료, 쿠키 삭제) 서버 세션은 남아 있어도 접근할 방법이 없다. 그 세션은 타임아웃될 때까지 메모리에 남는다.

**로그인 안 했는데도 세션이 생기나.** 생긴다. `getSession()`은 로그인과 무관하다. 장바구니, 임시 저장 등으로 로그인 전에도 쓰인다. 다만 외부 노출 페이지에서 무조건 세션을 만들면 봇이나 크롤러 요청마다 익명 세션이 쌓여 메모리를 먹는다.

**암호화를 잘하면 세션 쿠키는 신경 안 써도 되나.** 반대다. 암호화는 로그인 요청 1건을 보호하고, 세션 쿠키는 로그인 이후 전체를 보호한다. 순서를 정한다면 세션 쿠키가 먼저다.

**HTTPS면 쿠키가 안전한 것 아닌가.** 전송 구간은 안전하다. 다만 HTTP 접속이 같이 열려 있거나, `Secure` 속성이 없거나, XSS가 있으면 뚫린다. HTTPS는 필요조건이지 충분조건이 아니다.
