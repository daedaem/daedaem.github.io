## 두 축을 구분하자

자주 섞여 쓰이는데 **페이지 구성**과 **렌더링 위치**는 다른 축이다.

| 축 | 선택지 |
|---|---|
| 페이지 구성 | **MPA**(여러 페이지) / **SPA**(한 페이지) |
| 렌더링 위치 | **SSR**(서버) / **CSR**(클라이언트) / **SSG**(빌드 시점) |

관례적으로 MPA는 SSR과, SPA는 CSR과 짝을 이루지만 **고정된 짝은 아니다.**

## CSR

사용자의 요청에 따라 **필요한 부분만 응답받아 클라이언트에서 렌더링**한다.

1. 초기 화면 로드를 서버에 요청
2. 서버가 HTML·CSS와 초기 화면에 필요한 JS 청크를 준다. 번들이 크면 초기 로딩이 길어진다
3. 이후 특정 요소가 바뀌면 그 부분만 서버에 요청
4. 변경된 부분의 데이터만 받아 다시 그린다

| 장점 | 단점 |
|---|---|
| 페이지 전체를 새로 받지 않고 화면을 바꿀 수 있다 | 번들이 크거나 데이터 요청이 늦으면 **초기 콘텐츠 표시가 늦다** |
| 초기 이후 전환을 빠르게 만들 수 있다 | 검색 엔진의 JS 실행에 의존하므로 색인이 늦거나 결과가 달라질 수 있다 |
| 클라이언트에서 풍부한 상호작용을 제공하기 쉽다 | 저사양 기기의 JS 실행 비용이 커질 수 있다 |
| 서버 부하가 분산된다 | |

### 단점을 메우는 방법

**초기 로딩** — code splitting, tree shaking, chunk 분리로 JS 번들 크기를 줄인다.

**SEO** — 중요한 공개 경로를 빌드 시점이나 서버에서 HTML로 만든다. 검색 엔진만 다른 내용을 주는 방식은 피한다.

**둘 다** — CSR과 SSR/SSG를 섞는다. React는 Next.js(페이지별로 SSR·SSG 선택 가능), Vue는 Nuxt.js를 쓴다.

## SSR

**서버에서 완성된 HTML을 만들어** 보낸다. 페이지 전체를 렌더링한다.

| 장점 | 단점 |
|---|---|
| **SEO에 유리** | TTV와 TTI 사이에 간극이 있다 |
| 첫 응답에 콘텐츠가 있어 초기 표시가 빨라질 수 있다 | 매 이동마다 새로고침되는 깜빡임은 SSR이 아니라 MPA의 특성이다. SSR + 하이드레이션이면 이후 이동은 SPA처럼 움직인다 |
| | 캐시하지 않으면 요청마다 렌더링 비용이 든다 |

TTV와 TTI 사이 간극이란, 화면은 보이는데 아직 눌러도 반응하지 않는 구간이다. JS가 붙기 전이라 그렇다.

## SSG

**빌드 시점에 미리 HTML을 만들어 둔다.** 요청이 오면 만들어둔 파일을 그대로 준다.

SSR의 SEO 이점을 가지면서 정적 파일 서빙만 남아 서버 부하가 거의 없다. 대신 **내용이 바뀌면 다시 빌드해야 한다.** 누구에게나 같은 내용을 보여주고 업데이트가 잦지 않은 사이트에 맞는다.

> 이 블로그가 SSG다. Astro로 빌드해 정적 파일을 GitHub Pages에 올린다. 글이 바뀌면 다시 빌드해 배포한다.

## 무엇을 고르나

| 상황 | 선택 |
|---|---|
| 로그인 뒤 개인 화면처럼 검색 노출이 필요 없고 상호작용이 많음 | CSR을 우선 검토 |
| 공개 콘텐츠가 요청마다 달라지고 검색 노출이 중요함 | SSR과 캐시를 우선 검토 |
| 공개 콘텐츠를 배포 시점에 만들 수 있음 | SSG를 우선 검토 |
| 한 서비스 안에 공개 페이지와 개인 화면이 함께 있음 | 경로·컴포넌트별 혼합 렌더링 검토 |

업데이트가 잦아도 빌드를 자동화하거나 증분 재생성을 쓰면 SSG가 가능하고, SSR도 캐시하면 매 요청을 새로 렌더링하지 않는다. 선택은 SEO뿐 아니라 데이터 최신성, 개인화, 캐시 가능성, 서버 비용, 기기 성능을 함께 본다.
