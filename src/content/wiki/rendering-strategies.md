## 두 축을 구분하자

자주 섞여 쓰이는데 **페이지 구성**과 **렌더링 위치**는 다른 축이다.

| 축 | 선택지 |
|---|---|
| 페이지 구성 | **MPA**(여러 페이지) / **SPA**(한 페이지) |
| 렌더링 위치 | **SSR**(서버) / **CSR**(클라이언트) / **SSG**(빌드 시점) |

관례적으로 MPA는 SSR과, SPA는 CSR과 짝을 이루지만 **고정된 짝은 아니다.**

## CSR

사용자의 요청에 따라 **필요한 부분만 응답받아 클라이언트에서 렌더링**한다.

1. 초기 화면 로드를 서버에 요청
2. 서버가 필요한 리소스를 준다 — **모든 JS 파일까지 받으므로 초기 로딩이 오래 걸린다**
3. 이후 특정 요소가 바뀌면 그 부분만 서버에 요청
4. 변경된 부분의 데이터만 받아 다시 그린다

| 장점 | 단점 |
|---|---|
| 화면 깜빡임이 없다 | **초기 로딩이 느리다** |
| TTV와 TTI 사이 간극이 없다 | **SEO에 불리하다** — 빈 뼈대 HTML만 전달 |
| 초기 이후 구동이 빠르다 | |
| 서버 부하가 분산된다 | |

### 단점을 메우는 방법

**초기 로딩** — code splitting, tree shaking, chunk 분리로 JS 번들 크기를 줄인다.

**SEO** — pre-rendering. 요청자가 크롤러면 미리 렌더링해둔 HTML을 준다.

**둘 다** — CSR과 SSR/SSG를 섞는다. React는 Next.js(페이지별로 SSR·SSG 선택 가능), Vue는 Nuxt.js를 쓴다.

## SSR

**서버에서 완성된 HTML을 만들어** 보낸다. 페이지 전체를 렌더링한다.

| 장점 | 단점 |
|---|---|
| **SEO에 유리** | 화면 깜빡임 (매번 새로고침) |
| 초기 구동이 빠르다 | TTV와 TTI 사이에 간극이 있다 |
| | **서버 부하가 크다** — 매 페이지마다 서버가 일한다 |

TTV와 TTI 사이 간극이란, 화면은 보이는데 아직 눌러도 반응하지 않는 구간이다. JS가 붙기 전이라 그렇다.

## SSG

**빌드 시점에 미리 HTML을 만들어 둔다.** 요청이 오면 만들어둔 파일을 그대로 준다.

SSR의 SEO 이점을 가지면서 서버 부하가 없다. 대신 **내용이 바뀌면 다시 빌드해야 한다.** 누구에게나 같은 내용을 보여주고 업데이트가 잦지 않은 사이트에 맞는다.

> 이 블로그가 SSG다. Astro로 빌드해 정적 파일을 GitHub Pages에 올린다. 글이 바뀌면 다시 빌드해 배포한다.

## 무엇을 고르나

| 상황 | 선택 |
|---|---|
| 사용자와 상호작용이 많고, 개인 정보 위주라 **검색 노출이 필요 없다** | **CSR** |
| 자주 업데이트되고, **검색 노출이 필요**하며, 누구에게나 같은 내용 | **SSR** |
| 업데이트가 거의 없고, 검색 노출이 필요하며, 누구에게나 같은 내용 | **SSG** |
| 사용자마다 내용이 다르고, 빠른 인터랙션과 검색 노출이 **둘 다** 필요 | **CSR + SSR** (Universal) |

판단 기준을 하나로 줄이면 이렇다. **검색 노출이 필요한가, 그리고 내용이 사용자마다 다른가.** 그 둘이 방식을 결정한다.
